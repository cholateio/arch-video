# 查證清單

`check` 只確認座標指得到東西，不確認主張對不對。這份清單給**另一個查證者**用：一個全新的子代理，
有別的模型可用時優先交給別的模型。整理素材的人自己查自己寫的東西，容易照原本的理解再讀一次。

查證者只讀不改，逐條回原始檔。來源以素材「整理時的版本」記錄的 commit 為準；工作區裡還沒 commit 的修改不算現況。

## 要查的事（依優先順序）

1. **每條弧的「原因」「選擇」「沒採用」「影響」**：座標指到的地方真的支持這句話嗎？特別找這三種：
   - 把推測寫成〔有出處〕。
   - 拿已經被取代的舊設計、舊註解當成現在的原因。座標指到的註解或文件和現在的程式碼還一致嗎？
   - 說得比原文強（「永遠」「只會」「全部」「任何」）。找得到反例就是說過頭了。
2. **主旨**：它的每一句是否和「現況事實」一致，有沒有被某一條事實推翻。
3. **數值、數量、流程順序**：和記錄的 commit 一致嗎？推得的主張，算式對嗎？
4. **已實裝**：有沒有把未實裝、或程式在但沒有啟用的功能寫成現行事實。讀取端或另一個 repo 的狀態是否被寫得比實際完整。
5. **一句主張有幾個部分時**，每個部分都有座標支持嗎？
6. **故事線**：每條弧、每條資料流標的故事線合理嗎？有沒有一條弧其實也影響另一條故事線。
7. **簡化清單、排除、不一致**：有沒有漏掉明顯的項目。查證過程中發現文件或註解和程式碼不一致，就是「不一致」表漏掉的一列。
8. **機密與名稱**：素材與背景知識裡有沒有金鑰、內部位址、個資，或 owner 還沒同意出現的名稱。
9. **背景知識**：有沒有被拿來替專案的決定補原因。（網路來源本身的正確性不在這份清單的範圍，除非查證者可以連網。）

## 回報的格式

每個發現一條：嚴重度（高／中／低）、主張的編號、問題、證據（檔案與行號）、建議改法。按嚴重度排序。
最後列出：逐條查過而且沒有問題的弧、沒有查的部分。

- 高：成品照這句講會講錯（事實錯、原因錯、把沒實裝的講成有）。
- 中：說過頭、缺了時間或條件的限定、只描述了一個方向。
- 低：座標不夠支持、故事線標記、措辭。
