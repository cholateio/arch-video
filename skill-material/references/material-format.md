# 素材檔的格式

一個專案一個檔：`<素材庫>/<專案>.md`。背景知識另外放在 `<素材庫>/background/<主題>.md`，所有專案共用。

格式是固定的，`arch-material.mjs check` 會照這份文件檢查。寫完一定要跑它。

## 三個基本單位

### 主張

一句完整的命題，後面跟狀態，再跟座標：

```markdown
- **F3** 來源清單有八個帳號的時間軸。 〔有出處〕 `ingest:scripts/fetch.ts#SOURCES`
```

- **一句只講一件事**，要能單獨判斷對錯。「有上限」和「上限是十」各自的出處不同時，拆成兩條。
- **殘差規則**：專案文件已經寫清楚的，寫一句主張加座標就停，不把原文改寫成一段。
- **一件事只寫在一個地方。** 別處要用到同一個事實時寫「→F3」，不要再寫一次數字。「→」後面可以是主張、事實或一條弧的編號。
  理由：專案改一個數值，素材只需要改一條。
- 句子裡可以有反引號（例如 `workflow_dispatch`）；**狀態標記後面的反引號一律是座標**。

### 狀態

| 標記 | 意思 | 要附什麼 |
|---|---|---|
| 〔有出處〕 | 註解、文件、commit 或程式碼明白寫了 | 至少一個座標 |
| 〔推得〕 | 素材沒寫，但用算術或邏輯推得出來 | 下一行縮排寫「- 推法：…」；推導用到的來源也附座標 |
| 〔口述 2026-11-20〕 | owner 說的 | 日期。只有 owner 真的說過才可以用 |
| 〔不明〕 | 上面三種都不是。猜測作者的意圖屬於這一種 | 不附座標。主張本身寫成問句，`check` 會把它列進要問 owner 的清單。不只「原因」，任何一句（例如「所求」）查不到都可以標 |

觀察和推論分開：「看起來是為了……」不寫成〔有出處〕。

### 座標

寫在反引號裡，一律以來源的代號開頭（代號列在「整理時的版本」）：

| 寫法 | 指到什麼 |
|---|---|
| `` `ingest:scripts/fetch.ts#SOURCES` `` | 檔案裡的一段文字，通常是函式、常數、設定鍵的名稱。`#` 後面的字必須原樣出現在檔案裡；挑一段在檔案裡只出現一次的 |
| `` `ingest:docs/DEVELOPMENT.md#Easy to forget` `` | 文件的一個小節，`#` 後面是小節標題。標題裡有反引號時，取不含反引號的那一段 |
| `` `ingest:scripts/fetch.ts:77-100` `` | 行號。沒有名稱可以指的時候用（例如一大段註解）；行號容易跑掉，能用名稱就用名稱 |
| `` `ingest:scripts/lib` `` | 整個檔案或資料夾 |
| `` `ingest@0fd8535` `` | 一個 commit（原因寫在 commit 訊息裡的時候） |
| `` `bg:github-actions-schedule#B1` `` | 背景知識的一個條目 |

- 路徑相對於那個來源的根目錄。
- 不可以指向存放憑證的檔案。
- 一條主張可以有不只一個座標。現況事實需要背景知識時，把 `bg:` 的座標直接寫在那條主張後面。

## 編號

整份素材連續編，不在每一節重新算。

| 字頭 | 用在 |
|---|---|
| S | 故事線 |
| F | 現況事實 |
| A | 因果弧（`A1`）與它的主張（`A1.1`、`A1.2`…） |
| N | 架構的節點 |
| D | 資料流 |
| M | 簡化清單 |
| B | 背景知識的條目（每個背景檔各自從 B1 編起） |

更新素材時不重新編號：刪掉的編號不再使用，新增的往後編。成品會引用這些編號。

## 完整的骨架

````markdown
# 素材：<專案名稱>

## 總覽

格式版本：1
整理日期：2026-11-20
審核：還沒
範圍：<涵蓋什麼；不涵蓋什麼>

### 主旨
<一到兩段話：這個專案在做什麼、最重要的設計主張是什麼>

### 整理時的版本
| 代號 | 位置 | commit | 日期 |
|---|---|---|---|
| ingest | ~/kaf-posts-ingest | 0fd8535 | 2026-11-19 |

| 不在 commit 裡的來源 | 指紋 |
|---|---|
| `ingest:docs/LESSONS.md` | 3fa9c1d2e4b7 |

### 故事線
- **S1** <這個專案做的第一件事，一句話>。經過：<哪些節點與資料流>。共用：<和其他故事線共用什麼>。
- **S2** <第二件事>。經過：…。共用：…。

### 一手文件地圖
| 文件 | 講什麼 | 讀了多少 |
|---|---|---|
| `ingest:docs/LESSONS.md` | 事故與教訓，多數決定的原因在這裡 | 全部讀完 |
| `ingest:scripts` | 三個進入點與共用模組 | 全部讀完；測試只看檔名 |

### 審核紀錄
- （2026-11-20）owner：<對範圍、排除的決定>

## 現況事實
- **F1** <怎麼跑、有哪些部分、限制>。 〔有出處〕 `…`
- **F2** …

## 因果弧

### A1 <一句因果問題，以問號結尾>
- 故事線：S1
- 起點：<當時的痛點>
- 終點：結果：<現在的做法與它換來什麼>

#### 主張
- **A1.1** 所求：<當時要解決什麼、卡在什麼兩難>。 〔有出處〕 `…`
- **A1.2** 選擇：<現在的做法與數值>。 〔有出處〕 `…`
- **A1.3** 原因：<為什麼這樣選>。 〔有出處〕 `…`
- **A1.4** 沒採用：<考慮過什麼、為什麼放棄>。 〔有出處〕 `…`
- **A1.5** 影響：<換來什麼、代價是什麼、碰到邊界會怎樣>。 〔推得〕 `…`
  - 推法：<算式或推論>
- **A1.6** 帶得走：<換到別的專案也用得上的一句做法>

#### 需要的背景
- `bg:github-actions-schedule#B1` <觀眾要先知道這個，才聽得懂哪一句>

#### 物證
- `ingest:.github/workflows/ingest.yml#workflow_dispatch` <這是什麼：一段設定>
- `ingest:docs/LESSONS.md#2026-10-08` <一筆事故紀錄>

#### 缺口
- <文件沒記、靠考古或推斷才知道的部分；標明是推斷>

#### 口述
- （2026-11-20）<owner 說的話>

#### 後續發展
- （2026-11-19，`ingest@0fd8535`）<這個決定後來怎麼了>

## 架構拆解

### 節點
- **N1** Fetch（擷取區）：<它負責什麼>。 〔有出處〕 `ingest:scripts/fetch.ts`
- **N2** 資料庫（圖外）：<…>。 〔有出處〕 `…`

### 資料流
- **D1** Fetch 把新貼文寫進貼文表（S1）。 〔有出處〕 `…`
- **D2** Streams 從成員貼文裡找出直播連結，寫進直播表（S2）。 〔有出處〕 `…`

### 簡化清單
- **M1** 省略：<省略或合併了什麼>；實際：<實際是怎樣>。 〔有出處〕 `…`

| 內容 | 原因 | 位置 |
|---|---|---|
| <功能或資訊> | 未實裝／只有文件提到／機密或個資（只寫類型） | `…` |

## 不一致
| 項目 | 文件的說法 | 程式碼的實際情況 | 出處 |
|---|---|---|---|
````

## 各節的規則

### 總覽

- 「格式版本」「審核」「範圍」三行必填。「審核：還沒」在 owner 看過之後改成日期；還沒審核的素材不能拿去做成品。
- **主旨**：四百字以內。只說做什麼與最重要的設計主張，不列功能清單。
- **整理時的版本**：一個來源一列。位置寫成 `~/…`，而且要是 repo 的根目錄。一開始 commit 與日期填 `?`，
  整理完跑 `stamp`，把它印出來的兩張表整段貼上，不要手填。不是 git repo 的來源，commit 寫「無」。
  第二張表記「內容不在 commit 裡」的來源，用指紋比對有沒有變：不在版控裡的檔案（例如只留在本機的教訓紀錄），
  以及被主張引用、當時有還沒 commit 的修改的檔案。
- **故事線**：只記這個專案做哪幾件事、各自經過什麼、共用什麼。不排順序、不分主次、不寫橋接句。
- **一手文件地圖**：講「為什麼」的文件在哪、各講什麼、讀了多少。抽樣讀過不可以寫成全部讀完。沒有這類文件就寫一列說明沒有。
  不是檔案的來源（例如 `git log`）直接寫文字。這張表只記「讀過什麼」：檔案之後變了，不會因為它在這張表裡就被當成有主張受影響。
- **審核紀錄**：owner 在審核點對範圍與排除做的決定。素材 skill 只記錄，不代填。

### 現況事實

不屬於任何一條弧的事實：怎麼啟動、多久跑一次、有哪些部分、對外的介面、現在的行為與限制。
屬於某個決定的數值寫在那條弧的「選擇」，這裡不重複。

### 因果弧

- 標題是一句因果問題。一條弧只回答這一個問題。
- **故事線**：這條弧屬於哪一條（可以不只一條：`S1、S2`）。
- **起點**是痛點，**終點**以「結果」「推翻」「未決」其中一個開頭。
- **主張**至少要有「所求」「選擇」「原因」各一句；「沒採用」「影響」有就寫，素材裡沒有就不寫，不要編。
  - 同一種角色可以有不只一句（兩個原因就是兩條，各自標狀態）。
  - 「原因」分清楚兩層：為什麼需要這個機制，以及為什麼是這個數值。兩層的出處常常不同，分成兩條。
  - 「帶得走」是你的歸納，不標狀態，但要從這個決定的原因直接得出，不寫空泛的口號。
  - 「沒採用」只收考慮過而放棄、或已經被取代的做法，用過去式寫。還打算做的不放這裡，放「排除」。
- **需要的背景**：指到背景知識的條目，後面寫觀眾為什麼需要它。
- **物證**：只記座標和一句「這是什麼」。成品要用的時候再照座標去取實際內容。每條弧至少找一個。
- **缺口**：這條弧裡靠推斷或考古得來的部分。
- **口述**：owner 補充的話，註明日期。**不可以代填。**
- **後續發展**：決定被推翻或落定時往下追加，註明日期與 commit，不改寫上面的主張。

### 架構拆解

- **節點**：名稱、所屬分區、負責什麼。圖外的對象（使用者、外部服務、資料庫）也列，分區寫「圖外」。
  節點用角色命名，不用內部主機名稱。
- **資料流**：誰把什麼交給誰。**每一條都要在句子裡用括號標明故事線**（`（S1）`、`（S1、S2）`），
  成品才能一次只跟著一件事走。
- **簡化清單**：格式是「省略：…；實際：…」。架構圖少畫的連線、合併的節點、沒提的回程資料流都算。

### 排除與不一致

- **排除**：不可以出現在成品裡的內容。原因寫：未實裝、沒有啟用、只有文件提到、機密或個資、待 owner 決定。機密只寫類型與位置，不寫值。
- **不一致**：文件和程式碼說法不同的地方。主張一律採用程式碼的；這張表是給 owner 看的（他們可能想修文件）。沒有就留空表。

## 背景知識的格式

`<素材庫>/background/<主題>.md`，主題用小寫英數與連字號（`github-actions-schedule`）。一個主題一個檔。

```markdown
# GitHub Actions 的排程

用過的專案：kaf-posts-ingest

- **B1** <一句話的事實>。 〔有出處 2026-11-20〕 <https://docs.github.com/…>
- **B2** <查了但找不到公開說明的事>。 〔查不到 2026-11-20〕
```

- 狀態只有兩種：〔有出處 日期〕（後面附來源網址）與〔查不到 日期〕。日期是查證的那一天。
- 〔查不到〕的條目在句子後面用括號寫明是哪一種：官方頁面沒有寫、頁面讀不到、只找到非官方的說法。
- 只有被素材引用到的條目才算這個專案的背景；`check` 不會列出沒被引用的背景檔。
- 一個條目一句話，講外部服務或技術本身的行為，不提任何專案。
- 網址只留到頁面與錨點，去掉查詢參數。頁面轉址時記最後實際開到的網址。
- 條目只增不改號。內容過時了就改那一句並更新日期。
- 別的專案引用時，把專案名稱加進「用過的專案」。
- 查證超過 180 天的條目，再用之前要重新確認來源並更新日期（`check` 與 `status` 會提醒）。

## 哪些內容可以重新產生

| 內容 | 能不能從專案重新產生 |
|---|---|
| 主張、弧、架構拆解、排除、不一致 | 可以 |
| 口述、審核紀錄 | **不行**，重新整理時原樣搬過去 |
| 背景知識 | 不必重查，到期再確認 |
