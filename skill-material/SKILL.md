# arch-material — 把專案整理成可以拿來講解的素材

讀使用者的專案，整理成一份**素材檔**：帶出處的主張、因果弧（每個決定當初為什麼這樣選）、
聽懂它需要的背景知識、架構拆解。影片這類成品只從素材檔寫，所以素材裡沒有的東西，成品不會講。

核心精神：

- **素材決定成品的上限。** 原因、背景、哪幾件事各自成一條線，都要在這一步找齊。
- **以程式碼為準；原因要有出處。** 找不到原因就標〔不明〕並問 owner，不編一個聽起來合理的。
- **只記主張與座標，不改寫原文。** 專案文件寫清楚的事，一句主張加一個座標就夠。素材刻意不能直接貼成稿子。
- **一件事只寫在一個地方。** 一個數值、一個事實只有一條主張記它，其他地方用「→編號」指過去。
- **不在專案裡寫任何東西。** 對專案只讀；素材放在專案外面的素材庫。
- **機密不進素材。** 只寫類型與位置，不寫值。

`<skill>` 代表本檔所在的資料夾。`<素材庫>` 預設是 `~/arch-material/`，使用者有指定就照指定的。

```
<素材庫>/
  <專案>.md              一個專案一個檔
  background/<主題>.md   背景知識，所有專案共用
```

開始之前讀這兩份，後面每一步都照它們做：

- `<skill>/references/source-rules.md` — 怎麼讀、以誰為準、什麼算已實裝、機密、上網查背景的規則
- `<skill>/references/material-format.md` — 素材檔與背景知識的格式

## 先判斷是新整理還是更新

```bash
node <skill>/scripts/arch-material.mjs init            # 素材庫不存在時建立；已經存在不會動裡面的東西
```

- `<素材庫>/<專案>.md` 不存在：從步驟 1 做起。
- 已經存在：跳到最後的「更新」。

`<專案>` 用小寫英數與連字號，通常就是主要 repo 的名稱。

## 新整理（只在步驟 9 停下來等 owner）

### 1. 清點素材、確定範圍

- 列出收到的每一份素材和它的類型，替每個來源資料夾取一個短代號（例如 `ingest`、`site`）。
- 範圍：專案本身，加上使用者點名的部分。寫成一句話（「範圍：…」），也寫明不涵蓋什麼。
- 不讀存放憑證的檔案（清單見 `source-rules.md`）。
- 先建立素材檔，只放標題、「總覽」的幾行與版本表；版本表填代號與位置，commit 與日期先填 `?`（步驟 7 的 `stamp` 靠這張表找到來源）。
- 對每個來源跑 `git status` 與 `git log -1`，記下現在的 commit 與有沒有還沒 commit 的修改。
  **素材描述的是 commit 裡的內容**：還沒 commit 的修改不寫成事實；它碰到你要引用的檔案時，確認那句主張在 commit 的版本裡成立。
  整理到一半來源多了 commit，讀那個 commit 的差異，以新的為準。

### 2. 畫一手文件地圖，然後讀

- 先找出講「為什麼」的文件：設計紀錄、決策紀錄、教訓紀錄、審查紀錄、作者寫的介紹。記下每一份在哪、講什麼。
  專案沒有這類文件也照實記，這本身是 owner 需要知道的事。
- 讀：進入點、設定、核心模組一定要讀到；講「為什麼」的文件全部讀完；主要來源的 `git log` 全部掃過。
  只取一部分的輔助來源，`git log` 用關鍵字或路徑篩選就好，在文件地圖寫明是怎麼篩的。
- 素材量大就一個模組或一份文件派一個子代理去讀，要求它回報事實（附座標）、進入點、疑似未實裝的地方、
  疑似機密的位置（不含值），不貼大段程式碼。關鍵事實你要回原檔抽查。

### 3. 寫主旨與故事線

- **主旨**：一到兩段話，說完這個專案在做什麼、最重要的設計主張是什麼。寫不出來代表還沒讀懂，回步驟 2。
- **故事線**：這個專案其實在做哪幾件事，通常一到三件。每一件寫一句話、它經過架構的哪些部分、和其他故事線共用什麼。
  判斷方法：兩件事的輸入、輸出、觀眾關心的理由都不同，只是剛好共用一個排程或一張表，就是兩條故事線。
  這裡只記「有哪幾條」，不排順序、不分主次；那是成品自己的事。

### 4. 切出因果弧

一條弧只回答一個因果問題（「為什麼排程交給外部服務觸發？」）。邊界由故事決定，不由檔案或版本決定。

- 什麼值得一條弧：一個數值或上限、一條限制、一個分工方式、一個繞遠路的做法、一個「不做什麼」的選擇、一次事故之後的改動。
- 什麼不值得：沒有取捨的做法。問一次「當時有別的選擇嗎？選錯會怎樣？」，答不出來的是事實，放進「現況事實」。
  弧的數量沒有規定；每一條都要是第一次看這個專案的工程師會想問的「為什麼」。
- 每條弧寫：起點（當時的痛點）、終點（結果、被推翻、還沒定）、主張（所求、選擇、原因、沒採用、影響、帶得走）。
- 每一句主張標狀態並附座標。原因找不到出處又推不出來，標〔不明〕，主張本身寫成問句。
- 找**物證**：可以直接拿給人看的實物，例如一個常數、一行紀錄、一段設定、一筆實際數據。只記座標。
- 不屬於任何一條弧的事實（怎麼跑、有哪些部分、限制）放進「現況事實」。
  **誰在什麼情況下用它、用它需要準備什麼、第一步怎麼開始**也整理成事實（專案的說明文件通常寫了）：成品的結尾要講使用情境與怎麼開始，素材沒有就講不了。

### 5. 列出需要的背景，上網查證

對每條弧的每一句主張問一次：**第一次接觸的人要先知道什麼，才聽得懂這一句？**
常見的是外部服務的行為與限制（排程準不準、免費額度、保留幾筆）、協定或格式的特性、領域裡的慣例。

- 專案自己的事（它怎麼用這個服務、當時遇到什麼）：不用查，當成一般主張記在弧裡。
- 專案文件對**外部服務本身**的說法（「排程是盡力而為」「超過六十天會被停用」）：它是二手的，照樣去查官方的說法。
- 其餘的照 `source-rules.md` 的「上網查背景」去查，寫進 `<素材庫>/background/<主題>.md`，弧的「需要的背景」指過去。
- 先看 `background/` 裡是不是已經有這個主題：有就直接引用，並把這個專案加進「用過的專案」。
- 查不到就標〔查不到〕，不憑記憶寫。

### 6. 寫架構拆解、排除與不一致

- **架構拆解**：分區、節點、資料流、圖外的對象。每一條資料流標明屬於哪一條故事線。
- **簡化清單**：為了講清楚而省略或合併的東西，每一條寫省略了什麼、實際是怎樣。
- **排除**：不可以出現在成品裡的內容：還沒實裝的、只有文件提到的、機密與個資（只寫類型與位置）。
- **不一致**：文件和程式碼對不上的地方，以程式碼為準。

### 7. 蓋上版本並檢查

```bash
node <skill>/scripts/arch-material.mjs stamp <素材庫>/<專案>.md    # 印出現在的 commit 與指紋，貼進「整理時的版本」
node <skill>/scripts/arch-material.mjs check <素材庫>/<專案>.md
```

- `stamp` 會自己列出需要記指紋的來源：不在版控裡的檔案，以及有還沒 commit 的修改、又被主張引用的檔案。整段貼上，不要手改。
- 錯誤全部修掉；警告也要處理到沒有為止，處理不了的在審核點說明。「提醒」是資訊，不用處理到沒有。
- 被機密掃描擋下的句子：改寫成不含那個字串的說法。素材不需要逐字引用。

### 8. 交給另一個查證者

`check` 驗證的是格式和座標指得到東西，**不驗證主張對不對**。這一步不可以省，也不可以自己查自己。

- 把素材檔交給一個全新的子代理（有別的模型可用時優先交給別的模型），要它照 `<skill>/references/verify-checklist.md` 回原始檔逐條查證，只讀不改。
  給它：素材檔與背景知識的路徑、各來源的位置、這份清單的路徑。不給它你自己的結論。
- 它回報的每一條，你回原檔確認後再改素材：成立就改那一句（或拆成兩句、補座標、加進「不一致」）；不成立就在審核點說明為什麼不採納。
- 改完重跑 `stamp` 與 `check`。在審核點告訴 owner 查證找到幾條、改了幾條。

### 9. 審核點（停下來）

用一則訊息給 owner 下面這些，然後停下來等回覆。訊息是摘要，附上素材檔的完整路徑。訊息裡同樣不可以出現機密的值。

1. **主旨**：原文。
2. **故事線**：每條一句話。
3. **因果弧**：每條一句因果問題，以及它的原因是有出處、推得還是不明。
4. **背景知識**：這次查了哪些主題，每個主題的來源。
5. **要問 owner 的**：原因不明的決定（`check` 會列出來）、查不到的背景、拿不準的事、公開的名稱可不可以出現在成品裡。寫成可以一句話回答的問句，**每一題都寫明沒回答時的預設**（原因不明的預設是成品不講它的原因；公開名稱的預設是用角色代稱）。
   要 owner 決定的事在這一則訊息裡一次列完，owner 回覆後直接照做，不為同一件事再問一次。
6. **排除與不一致**：哪些內容不會出現在成品裡；文件和程式碼哪裡對不上。
7. **讀了多少**：哪些讀完、哪些只讀一部分、哪些沒讀。在素材裡發現寫死的金鑰、內部位址或個資時，告訴 owner 類型和位置（不含值）。

owner 回覆之後：

- owner 補充的原因：把那條主張的狀態改成〔口述 日期〕，內容照 owner 說的寫，不潤飾成 owner 沒說過的意思。
  其餘的話記進那條弧的「口述」。**owner 沒有回答的，維持〔不明〕，不代填。**
- owner 對範圍、排除的決定記進「總覽」的「審核紀錄」。
- 把「審核：還沒」改成「審核：<今天的日期>」，再跑一次 `check`。
- owner 說某個原因不重要、不用放：那條主張維持〔不明〕，把這個決定連同編號記進「審核紀錄」。
  之後更新素材時，審核紀錄裡已經有決定的問題不再問一次。
- 告訴 owner 素材檔的路徑，以及還留著幾條〔不明〕（成品不會講這幾條的原因）。素材審核過之後才能交給 arch-video 做影片。

## 更新（素材檔已經存在）

素材不用跟著每一次改動維護。只在要用它之前（做影片之前）或 owner 要求時更新。

```bash
node <skill>/scripts/arch-material.mjs status <素材庫>/<專案>.md
```

- 「素材是最新的」：不用做任何事，告訴 owner。
- 「素材記錄的內容沒有過期，但來源有還沒 commit 的變動不在素材裡」：素材描述的是記錄的那個 commit。
  把它列的變動告訴 owner，由 owner 決定現在就用，還是等 commit 之後再更新素材。不要自己把還沒 commit 的內容寫進素材。
- 「建議整份重新整理」：照建議做，從步驟 1 重來。**原本的口述與審核紀錄原樣搬到新的素材檔**，那是唯一無法重新產生的內容。
- 其餘情況照它列的清單做：
  1. **引用到變動檔案的條目**：逐條回原檔重新查證。還成立就不動；數值變了就改那一條；
     做法被拿掉或推翻，在那條弧的「後續發展」追加一段，寫明日期、commit 與原因，**不改寫原本的主張**，並把終點改成「推翻」。
  2. **變了、但素材沒有引用的檔案**：讀這段期間的 commit 訊息與這些檔案，判斷有沒有新的功能、新的決定、
     進入點或設定的增減。有就加事實或加一條弧，需要的背景照步驟 5 補。
  3. **進入點、設定、流程檔有變動時**，即使某些主張引用的檔案沒變，也要重新確認這些功能仍然從進入點走得到。
  4. **口述和新的程式碼矛盾**：不刪口述，在它後面註明「和 <commit> 之後的程式碼不一致，待 owner 確認」，列進要問 owner 的清單。
  5. 背景知識該重新確認的：重新查一次來源，更新日期。
- 新增或改寫的主張照步驟 8 交給另一個查證者，範圍只給這次動到的條目。
- 更新完跑 `stamp`，把版本表換成新的，再跑 `check`。**跑 `stamp` 之前先再跑一次 `status`**：來源可能在你更新的期間又多了 commit。
  `stamp` 只記下現在的版本，不查證；它印出「版本會從 … 換成 …」而你還沒看過那段變動時，不要貼上那張表。
- 給 owner 一張短的清單：哪幾條改了、新增了哪些、哪條弧多了「後續發展」、有什麼要問。
  有新增的弧，或既有的主張被推翻時，把審核改回「還沒」，等 owner 看過那幾條再標日期；只改數值不用。

## 不可以做的事

- 不在使用者的專案裡建立或修改任何檔案，也不替使用者 commit。
- 不讀 `.env`、金鑰檔、憑證；不把金鑰、密碼、內部位址、人名、電子郵件的值寫進素材、背景知識或給使用者的訊息。
- 不替 owner 填口述，不替〔不明〕的原因編理由。
- 不把還沒實裝或打算做的功能寫成事實；它們只出現在「排除」。
- 上網查背景時，查詢字串與開啟的網址裡不放專案名稱、帳號、內部名稱、程式碼、紀錄或數值。
- 不對素材庫執行 `git init`、同步或上傳；要不要備份由 owner 決定。
- 不為了通過檢查而刪掉主張或換成指得到的假座標；座標指不到，代表那句主張還沒有查證過。
