# 素材 skill 設計規格

日期：2026-11-19
狀態：**owner 已確認（2026-11-20）**。第一階段（素材 skill 與格式）與第二階段（影片 skill 讀素材庫）已實作；第三階段（重做同一支影片來比較）還沒做。
標記：**[user]** = user 決定；**[mine]** = 我的決定，owner 可推翻。

## 1. 為什麼要做

- **[user]** 內容才是主角：好的素材是好的解說影片的第一步。把「整理素材」和「生成影片」拆成兩個 skill。
- **[user]** 整理素材可以參考 owner 的開發記事做法（殘差規則、因果弧、物證、缺口與口述）。
- **[user]** 看完重做的影片後指出兩個問題，都出在素材：
  1. 講解會跳：前一刻在講貼文，下一刻因為架構圖上有直播那條線就講直播，沒有橋接。
  2. 背景交代不清：GitHub 的排程為什麼是盡力而為、來源為什麼只留 25 則，這類外部服務的知識很關鍵，卻沒有交代。
- **[mine]** 這次對話裡 owner 回饋過的內容問題（原因被濾掉、背景缺席、講解跳躍、大綱兩小時內過期）都發生在整理素材的階段。

## 2. 三層

| 層 | 內容 | 誰的 |
|---|---|---|
| 素材庫 | 帶出處的主張、因果弧、背景知識、物證、缺口，以及「這個專案做哪幾件事」（故事線有哪幾條）。不決定順序與輕重 | 素材 skill，可以給不同出口用 |
| 編排 | 故事線的順序與主次、挑哪幾條弧、哪裡著重、線與線之間的橋接 | 每個出口自己的 |
| 成品 | 影片、文章 | 每個出口自己的 |

- **[mine]** 現在的 `brief.md` 把前兩層混在一起（「講深的決定是哪幾個」「開場用哪一條」是編排）。拆開之後 `brief.md` 這個格式退役。
- **[mine]** 這一版只做影片這個出口。部落格維持現狀，見第 8 節。

## 3. 對開發流程的影響

- **[user]** 開發專案時不受影響：專案照常把開發過程寫進自己的文件，做影片時才用素材 skill 去取。
- **[user]** 不希望每個專案裡都多出素材資料夾；也擔心改了程式或加了功能之後，素材要跟著改很多地方。
- **[mine]** 所以素材 skill **不在專案裡寫任何東西**，對專案只讀。素材集中放在專案外面的一個素材庫（第 4 節）。
- **[mine]** 素材不是要跟著專案同步維護的文件，而是**記了版本的快取**：平常不用管它，要做影片時才檢查有沒有過期、
  只更新受影響的部分（第 5 節）。
- **[mine]** 素材的品質上限是專案自己留下的紀錄。素材 skill 會回報「哪些決定找不到原因、哪些背景查不到」，
  owner 可以選擇回專案補，但這不是使用它的前提。

## 4. 素材庫的格式

位置：**[mine]** 專案外面的一個素材庫，預設 `~/arch-material/`（原本提的「放在各專案裡」因為 owner 的顧慮改掉）。
它預設是私人的，所以缺口與口述不會跟著公開的 repo 公開。建立時權限設成只有 owner 的帳號讀得到。
**[user]** 不考慮同步到別台電腦；skill 不對素材庫執行 `git init`、同步或上傳。

```
~/arch-material/
  background/<主題>.md   背景知識，所有專案共用（例如 GitHub Actions 的排程、某個外部服務的限制）
  <專案>.md              一個專案一個檔
```

一個專案一個檔，裡面依序是這幾節。這一版不拆檔。確切的格式（編號、狀態標記、座標的寫法）在 `skill-material/references/material-format.md`，
並由 `arch-material.mjs check` 檢查；這份規格只記設計上的決定。

| 節 | 內容 |
|---|---|
| 總覽 | 格式版本、審核狀態、範圍、主旨、故事線、一手文件地圖、整理時的版本、審核紀錄 |
| 現況事實 | 不屬於任何一條弧的事實（怎麼跑、有哪些部分、限制） |
| 因果弧 | 每條弧一小節 |
| 架構拆解 | 分區、節點、資料流（影片用），以及簡化清單 |
| 排除 | 不可以出現的內容：還沒實裝的、機密與個資的類型與位置（不含值） |
| 不一致 | 文件和程式碼對不上的地方，以程式碼為準 |

每一節哪些部分是可以重新產生的、哪些不行：

| 部分 | 能不能從專案重新產生 |
|---|---|
| 主張、弧、架構拆解、排除 | 可以。它們是讀專案得到的，記了版本 |
| owner 的口述與在審核點確認過的事 | **不行**。這是素材庫唯一不可取代的內容 |
| 背景知識 | 不必重查。查過一次就留著，別的專案也用得上；超過 180 天再用時重新確認來源 |

### 4.1 主張是最小單位 **[mine]**

- 一個主張是**一句完整的命題**，後面跟座標（`檔案#小節` 或 `檔案:行號`、commit）與狀態。
- 狀態：`有出處`、`推得`（寫出怎麼推的）、`口述`（owner 說的，註明日期）、`不明`。
- **殘差規則**：專案文件已經寫清楚的，只寫一句主張加座標，不把原文改寫成一段。素材刻意不能直接貼成稿子。
- 照概念整理，不照檔案整理。
- **一件事只寫在一個地方。** 一個數值、一個事實只有一條主張記它，其他地方用編號指過去。
  依據：2026-11-19 來源 repo 移除三個搜尋來源，舊的 `brief.md` 有 8 個條目要改（N1、N3、F6、K3、K4、K5、K7、K8），
  因為「11 個來源」和搜尋來源的事實被抄在好幾處。
- 座標優先用小節名稱、函式或設定的名稱，行號只當輔助；行號跑掉不算素材過期。

### 4.2 總覽

1. **主旨**：一到兩段話，說完這個專案在做什麼、最重要的設計主張是什麼。寫不出來代表還沒讀懂，不往下做。
2. **故事線**：這個專案其實在做哪幾件事（通常一到三件），每一件的一句話、它經過架構的哪些部分、和其他故事線共用什麼。
3. **一手文件地圖**：講「為什麼」的文件在哪、各講什麼、讀了多少。沒有這類文件也照實記。
4. **整理時的版本**：每個 repo 的 commit 與日期；commit 釘不住的來源另外記內容的指紋：不在版控裡的檔案（例如只留在本機的教訓紀錄），
   以及被主張引用、當時有還沒 commit 的修改的檔案。素材描述的是 commit 裡的內容；來源裡沒被素材引用的未 commit 變動只提醒，不算過期。
5. 弧的清單不寫在檔案裡（照「一件事只寫在一個地方」），由 `check` 從各條弧印出來。

### 4.3 因果弧

一條弧只回答一個因果問題。邊界由故事決定，不由版本或檔案決定。

- **因果問題**（一句）；**起點**（痛點）→ **終點**（結果、推翻、未決）。
- **主張與座標**：所求、選擇、原因、沒採用的、影響、帶得走的做法。每一項是一句主張。
- **需要的背景**：指到素材庫 `background/` 裡的條目。
- **物證**：可以直接拿出來給人看的實物（一個常數、一行紀錄、一段設定、一筆實際數據），只給座標。
- **缺口**：文件沒記、靠考古或推斷的部分，標明是推斷。
- **口述**：owner 補充的話。素材 skill 不代填，只在 owner 說了之後記下來並註明。
- **後續發展**：決定被推翻或落定時往下追加，不改寫原本的內容。

### 4.4 背景知識（新的一步，所有專案共用）

- 對每條弧的每個主張問一次：**第一次接觸的人要先知道什麼，才聽得懂這一句？** 列出來的就是需要的背景。
- **[user]** 允許上網查。**[mine]** 規則：
  - 優先查官方文件；查到的每一條記來源網址、查證日期、一句話的內容。不憑記憶寫。
  - 查詢字串只放公開的服務與技術名稱，不放專案名稱、帳號、內部名稱。
  - 專案文件自己已經解釋的，只給座標。
  - 查不到就標 `查不到`，列進要問 owner 的清單。
- 一個主題一個檔，放在素材庫的 `background/`，不屬於任何一個專案。用過它的專案記在檔案裡。

### 4.5 架構拆解

- 分區、節點、資料流，以及圖外的對象。每條資料流標明屬於哪條故事線。
- **簡化清單**：為了講清楚而刻意省略或合併的東西，每一條寫省略了什麼、實際是怎樣。

## 5. 素材 skill 的流程

1. 清點素材、確定範圍。不讀憑證檔。
2. 畫一手文件地圖，讀完講「為什麼」的文件、進入點與核心模組；`git log` 全部掃過。
3. 寫主旨與故事線。
4. 切出因果弧，寫主張與座標，標狀態，找物證。
5. 列出需要的背景，上網查證。
6. 寫架構拆解、簡化清單、排除清單。
7. 蓋上版本、跑格式檢查，再**交給另一個查證者**回原始檔查主張對不對（格式檢查查不出內容錯誤；第一次實跑查出 13 處）。
8. **審核點（停下來）**：給 owner 主旨、故事線、弧的清單、背景知識與來源、查不到與原因不明的問題、排除清單。
   owner 的回覆記進對應的「口述」。
9. **更新**：不是每次改程式都要做，只在要用素材時（做影片前）或 owner 要求時做。
   - 比對素材記錄的版本和 repo 現在的版本；一樣就什麼都不做。
   - 不一樣時，讀這段期間的 `git log` 與變動的檔案，用座標找出**引用到這些檔案的主張**，只重新查證這幾條。
   - 給 owner 一張短的清單：哪幾條變了、新增了哪條弧、哪條弧多了「後續發展」。owner 的口述原樣保留。
   - 預期的改動範圍（估計，還沒實測）：

     | 專案的變動 | 素材要改的 |
     |---|---|
     | 重構、修 bug，行為與決定沒變 | 不用改 |
     | 改一個數值 | 一條主張 |
     | 加一個功能 | 加一條弧，或在現況事實加幾條；其他弧不動 |
     | 拿掉或推翻一個核心的做法 | 相關的幾條弧各追加「後續發展」，這是改動最多的情況 |

增量更新找不到的情況（寫進 `skill-material/references/source-rules.md` 第 7 節，更新時要自己看）：
全新的功能與決定（素材裡還沒有條目）、進入點或設定變動造成的間接影響、數量類的事實、推得的主張。
記錄的 commit 不在現在的歷史上，或被引用的檔案有一半以上變了，就整份重新整理。

機密規則整套搬進 `skill-material/references/source-rules.md`（不讀憑證檔、哪些類別不進素材、只寫類型與位置）。
素材檔與它引用的背景知識都會被機密掃描；掃描程式和影片 skill 共用同一份。
上網查背景只查公開的服務與技術名稱，只開不需要登入的公開頁面；拿不準是不是公開的名稱不查，先問 owner。

## 6. 影片 skill 的改動

- 步驟 1 到 3（清點、整理、內容確認）移到素材 skill。影片 skill 從素材庫裡那個專案的檔案開始。
- **[user]** 一律要求先跑素材 skill，不保留「沒有素材時自己整理」的舊路徑。
  素材不存在、還沒經過 owner 審核、或已經過期（`status` 不是「最新」）時，影片 skill 停下來，先跑素材 skill。
- 工作資料夾（編排、架構圖、分鏡、預覽、成品）也放在專案外面，預設是素材庫裡的 `video/<專案>/`，不寫進專案。
- **編排**寫在工作資料夾的 `treatment.md`：採用的主旨、故事線的順序、每條故事線挑哪幾條弧、
  故事線之間的橋接句、每個決定要用到哪些背景與物證。這是新的審核點一。
- **架構圖照故事線走**，不再要求把每條連線依序走完：一條故事線走完它經過的節點與連線，換下一條時先講一句橋接
  （「同一個排程還順便做第二件事」）。
- **背景知識在第一次用到的地方交代**，用一到兩句，放在講那個決定之前。
- **主張是封閉的，細節是開放的**：影片可以依座標回去讀原文、取物證的實際內容，但不可以講素材裡沒有條目的主張。
  **[mine]** 用程式守住：分鏡寫 `meta.material`，每個場景寫 `basis`（它根據的素材編號）；`build` 先確認素材存在、審核過、沒過期，
  再核對編號在素材裡、而且不是〔不明〕的主張或〔查不到〕的背景。它只核對編號，旁白有沒有多講仍然靠審核。
- 物證優先用在終端機、清單視窗、數字的畫面上，取代「示意」的內容。

## 8. 和部落格的關係

- **[mine]** 這一版兩邊沒有關聯：部落格繼續用 vault 裡的開發記事流程與自動產文，素材 skill 不讀寫 vault 的部落格區，也不改部落格的流程。
- 兩邊共用的是做法（因果弧、殘差規則、物證、缺口與口述），不是檔案或程式。
- 代價：同一個專案會被整理兩次，兩份可能不一致。
- **[mine]** 這一版只做一個方向的銜接：專案已經有開發記事筆記時，owner 可以把它當成一份素材交給素材 skill。
  它被當成二手資料：用來找文件地圖和 owner 的口述，裡面的事實仍然要回專案查證。
- 之後要不要讓部落格也吃素材庫，等影片這邊在兩三個專案上跑順了再決定。

  結尾拿掉「怎麼開始」，大部分情況不需要。
  **[mine]** 腳本規則多一條「用詞要指得出是哪一個東西」：外部產品與服務說名字，籠統的詞第一次出現要說清楚是哪一個，同一個詞只指一種東西；
  「怎麼開始」預設不講，使用者要求才加。

## 11. 設計審查（2026-11-20，另一個模型審這份規格）

採納的：格式要能機械檢查並附檢查程式；增量更新找不到的情況要寫明並有整份重來的條件；
新鮮度不能只看 commit（未 commit 的修改、不在版控的來源、歷史被改寫）；「以誰為準」「什麼算已實裝」「不一致」「機密的類別」
要完整搬進素材 skill；素材庫的權限；上網查背景前先分類主題；故事線在素材層只記「有哪幾條」。

沒有採納的，以及原因：

- 用去識別化的代號取代專案名稱與路徑：素材庫是只有 owner 讀得到的本機資料夾，換成代號會讓 owner 自己也讀不懂。
- 替每個物證登錄內容雜湊與允許使用的範圍：影片 skill 開始前已經要求素材是最新的，分鏡也仍然會被機密掃描。
- 用 YAML 或 JSON 當素材格式：owner 要能直接讀這份檔案；改用固定寫法的 Markdown 加上檢查程式。
