## 1. 目標

一個 Claude Code skill：`/arch-video <repo>`。輸入一個 repo，輸出一支有旁白、燒錄字幕、
章節結構的 1080p 技術架構解說影片（mp4）。

- **[user]** 輸入是一個 repo；先支援 skill / MCP 類專案；觀眾是工程師。
- **[user]** 實際使用時輸入常是一批混合的素材（skill、程式碼、技術文件）。做影片前要先摘要並對齊：
  - 以程式碼為準；觀眾只需要知道現有的功能，還沒做或打算做的功能完全不提。
  - **[user]**（2026-11-19，看過三支實測影片之後）影片不可以只是報告流程和設定值。要講「為什麼這樣設定」和「這樣設定的影響」，
    原因從註解與設計文件裡找。目標是從報告影片轉成生活化、看完有收穫的知識影片。
    - **[mine]** 做法：現況以程式碼為準，原因以註解、設計紀錄、教訓紀錄、commit 訊息為準；大綱加「決策」一節
      （問題、選擇、原因、沒採用的、影響、帶得走的做法）；影片主體以決定為單位。查不到原因不編，列出來問使用者。
    - **[mine]** 「考慮過、沒採用的做法」可以當成現行決定的對照來講；「打算做的功能」仍然不提。
    - **[user]** 講法參考使用者另一個專案的寫作規範：每一步先講所求、因果明講、抽象的東西馬上配一個具體情況、
      一正一反舉例、比喻用平實的話講且不演戲。
    - 依據（實測）：三支影片的旁白裡，講原因的句子只有 2% 到 6%。
  - 程式裡的機密不可以洩露。
  - 技術文件裡有架構圖也用 arch-blueprint 重畫，文件的圖只參考分層。
  - 寫腳本之前多停一次，讓 owner 確認內容。
- **[user]** 整理素材之後，影片不可以變成程式碼的流水帳：一切從需求想起、由架構藍圖帶動介紹、用範例補證，
  不特別偏向程式碼，也不要太詳細。做法 **[mine]**：大綱是素材庫、不是腳本的目錄；架構圖之後的細節都要掛在圖上的節點或連線；
  `file`、`terminal`、`tree` 只當佐證且不超過場景總數的三分之一（程式會警告）；旁白講做什麼、為什麼、交給誰，不講怎麼寫的。
- **[user]** 產品本體是「repo → 章節 → 一畫面一概念的分鏡 → 旁白逐句對齊」這條流程；
  視覺是可抽換的主題。
- **[user]** 形式是 skill，不另做 agent（中途要在主對話停下來審核一次）。
- **[user]** Windows 原生與 WSL 都要能跑，不能莫名卡住。

### 試作與過關標準

- **[user]** 第一支講 arch-blueprint skill。
- **[user]** 試作 2–3 分鐘、1080p、16:9。過關：除了配音音色以外，owner 願意直接公開。
- **[user]** 不設預設長度：有時要講的不只專案本身，還有額外功能，長度由要講的內容決定。
  - **[user]** 2026-11-21 修正：kaf-posts-ingest 第四版小專案講了 14 分鐘，太長。改成編排時先定目標長度（沒指定時照專案大小給，小專案 6 分鐘），
    在審核點一讓使用者確認；講深幾條弧由長度決定。**[mine]** 做成程式檢查：分鏡寫 `meta.length` 與各章 `length`，超過就警告；正式影片沒寫目標也警告。
  - **[user]** 2026-11-21 看完第五版（6 分 28 秒）：接近成品，除了畫面的豐富度與配色風格，其他都沒問題。

## 2. 流程

| # | 階段 | 產物 | 說明 |
|---|---|---|---|
| 0 | doctor | 體檢報告 | 檢查 Node、瀏覽器、ffmpeg、配音連線；缺什麼明講怎麼補 **[mine]** |
| 1 | digest | `brief.md` | 清點素材、以程式碼為準整理成內容大綱：主題與事實（附出處）、架構拆解、排除清單、不一致 **[user]**；格式 **[mine]** |
| 1a | **審核點一** | owner 放行或退回 | 確認主題、架構拆解、排除清單 **[user]** |
| 1b | diagram | `overview.svg` | 用 arch-blueprint 依程式碼畫 **[user]** |
| 2 | script | 章節 → 場景 → 旁白句 | 只從大綱寫；一個場景只講一個概念 |
| 3 | storyboard | `storyboard.json` | 每個場景：元件類型、資料、旁白句、觸發點、進場轉場 |
| 4 | preview | 每場景一張靜態圖 | 審核用 **[mine]**。開頭先掃描機密，發現就停；預覽不配音（時間用字數估算），owner 確認腳本之前旁白不送到配音服務 **[mine]** |
| 5 | **審核點二** | owner 放行或退回 | 腳本、分鏡一起審 **[user]** |
| 6 | tts | 每句一個音檔 + 秒數 | 逐句合成、以「文字＋音色」為鍵快取 **[mine]** |
| 7 | timeline | 各句起訖時間 | 由音檔秒數加句間留白算出，驅動動畫與字幕 **[mine]** |
| 8 | compose | HyperFrames HTML | 分鏡資料 + 元件庫 + 主題 |
| 9 | render | mp4 | 畫面、旁白、燒錄字幕 |
| 10 | check | 自檢報告 | 抽格看圖、長度與字幕溢出檢查 |

arch-blueprint 自己要求的「畫圖前確認拆解」就是審核點一，不另外再停 **[mine]**。
原本只停一次（拆解併入第 5 步）；owner 於 2026-11-19 同意多停一次，因為素材多的時候理解錯了要整份重寫。

整理素材的規則寫在 `skill/references/source-rules.md`。參考了公開的程式碼拆解技能的做法 **[mine]**：
每個說法附出處、沒有出處就不當成事實、記錄讀了多少、觀察與推論分開。

給 Claude 的操作步驟寫在 `skill/SKILL.md`（它的步驟編號和這張表不同）；第 0 步是 `arch-video doctor`，第 4、6–10 步是 `arch-video build`。
成果放在工作資料夾：預設是主要 repo 的 `docs/video/`（大綱、分鏡）與 `docs/video/out/`（產出，不進版控）**[mine]**。

## 3. 視覺

主題可切換：`skill/themes/<名稱>.mjs` 放該主題的所有設計數值，`skill/themes/base.css` 與場景元件只引用這些值。

- **[user]** 預設主題是 `night`（深色）：近黑底、暖白線條與文字、版面置中、字幕白字無底框。
- **[mine]** 保留 `blueprint`（淺色）：紙色 `#faf8f4`、墨黑 `#1a1a1a`，沿用 arch-blueprint 的配色。
- **[user]** 字級調小：大字標語最大 96px、標題最大 104px（原本 190px 與 160px 太大）。
- **[user]** 兩個強調色。**[mine]** 分工：強調色標示「現在正在講的東西」；
  第二強調色只在需要和強調色區分時使用（例如流程裡不同性質的步驟）。
- **[user]** 彩色圖示。**[mine]** 用 Phosphor 的 duotone 圖示，顏色跟著主題的強調色。
- **[mine]** arch-blueprint 的圖放進影片時自動換成主題的底色與線條色，arch-blueprint 本身不改。
- **[mine]** 自己的特色保留在：線條逐筆畫出、等寬字（JetBrains Mono）、工程圖的裁切標記與尺寸標註線。
- **[user]** 不能全是流程圖，表現方式要有變化（2026-11-19 看過第一支影片後再次強調）。規則 **[mine]**：
  - 同一種元件不連續超過兩次；三分鐘以上的影片至少用六種元件。
  - 原本「流程圖類場景不超過總長三分之一」的上限取消：owner 要求架構圖多花篇幅講節點與資料流。
- **[user]** 架構圖要逐區講解節點，並把資料流一條一條走過。
- **[user]** 開場從需求與痛點出發，可以用情境例子，不要開門見山介紹專案。
- **[user]** 結尾要完整：**[mine]** 重點回顧、適合與不適合、怎麼開始、一句帶走的話、片尾卡。
- **[user]** 旁白與字幕繁體中文；圖內文字英文（arch-blueprint 規則）。

### 場景元件（固定一套，模型只填資料）**[user]**

- 已完成十二種：`title`、`statement`、`file`、`map`、`flow`、`chat`、`compare`、`list`、`stat`、`tree`、`cycle`、`terminal`。
- **[user]** 畫面與動畫單調（2026-11-19 看過四支影片後）：都是對話框開頭、流程圖拉近拉遠、程式欄加一行說明、放大文字。

  參考影片的做法是把少數幾種小零件在每個場景重新組合，而不是一個場景套一種全螢幕版型。
- **[mine]**（使用者同意）方向改成「版面 × 零件」：模型仍然只填資料、排版仍由程式負責，但一個場景不再等於一個元件。

  做法 **[mine]**：每句旁白的 `text` 是字幕、`say` 是實際唸的話；專有名詞列在分鏡的 `meta.properNouns`，

- **[user]** 動畫一律比旁白先到。**[mine]** 做法：元素在旁白講到它的那個子句開始之前 0.8 秒出現；第一句旁白在場景內容出現 0.5 秒後才開始；元素排在旁白講完之後會警告。

## 7. 驗證結果（2026-11-19，WSL）

用 HyperFrames 0.9.67 與 node-edge-tts 1.2.12 實測，兩支約 11 秒的測試片在 `out/`（不進版控）。

- **引擎可用**：不需 sudo。無頭 Chrome 由 `hyperframes browser ensure` 下載到使用者快取目錄，約 19 秒。
- **渲染速度**：11.8 秒、1080p、30fps 的片子約 6 秒渲染完。
- **動畫**：GSAP 的 SVG 筆畫動畫（`strokeDashoffset`）與變色可用；CSS `@keyframes` 動畫也能逐格定位。
- **音軌**：多個 `<audio>` 依各自的 `data-start` 正確混入。`<audio>` 必須有 `id`，否則渲染出來沒聲音。
- **配音**：`zh-TW-HsiaoChenNeural`、`zh-TW-YunJheNeural` 都能合成，每句約 0.7 秒，附字詞時間戳。
- **觸發點要用字元位置**：斷詞會把詞切開（「十二個」被切成「十」「二個」），
  所以把各段文字接起來找關鍵詞的起始字元，再回推時間，不能直接比對詞。

### 實測後新增的決定 **[mine]**

- **關閉遙測**：HyperFrames 預設會回傳使用統計。skill 執行時一律設 `HYPERFRAMES_NO_TELEMETRY=1`。
- **不用上傳類指令**：`publish`、`share`、`cloud` 會把專案或影片傳到 HeyGen，一律不用。
  HyperFrames Pro 的範本與雲端渲染是付費功能，本專案不使用；本機渲染免費。
- **字型與 GSAP 隨專案附帶**：預設做法是渲染時從 Google Fonts 與 CDN 下載，受限的網路可能擋。
  改成用 npm 安裝 GSAP、字型檔放進專案。
- **固定版本**：鎖定 `hyperframes` 與 `node-edge-tts` 的確切版本，兩台機器產出一致。
- **審核預覽圖**用 `hyperframes snapshot`，交付前跑 `hyperframes lint`。
- **離線配音備案**：HyperFrames 內建本機語音模型 Kokoro，說明列出支援中文，但需要 Python，尚未測試。
