# 腳本規則

寫旁白與分鏡時遵守。標「程式會檢查」的規則，違反時 `arch-video build` 會報錯或警告；
其餘靠寫的人自己把關。

**觀眾是沒碰過這個專案的工程師。** 他們看完要帶得走兩樣東西：這個專案現在怎麼運作，
以及**為什麼這樣設計**：當初遇到什麼問題、怎麼選、換來什麼、付出什麼。
只報告「有哪些流程、數值是多少」的影片，觀眾學不到東西，算是沒做好。

**內容的來源是素材檔與編排。** 素材檔由 arch-material 整理、owner 審核過；編排（`treatment.md`）決定講哪些、照什麼順序。五條底線：

- **主張是封閉的。** 講到功能、行為、原因、背景的旁白，都對得到素材裡的一個條目，並記在那個場景的 `basis`；
  開場的情境例子與串場的句子除外。（程式會檢查 `basis` 的編號在不在素材裡）
- **細節是開放的。** 要把物證放上畫面時，照座標回原檔取實際內容。回去只取那個物證，不順便帶回新的主張。
- 講到原因的旁白，都對得到素材裡一條〔有出處〕〔推得〕或〔口述〕的主張。**標成〔不明〕的原因不講，不可以自己編。**
- 還沒實裝或打算做的功能、素材「排除」裡的內容完全不提，包括結尾。可以講現在的行為與限制，也可以講當初考慮過、沒採用的做法（見「主題怎麼講」）。
- 機密與個資不進旁白、不進畫面。（程式會檢查常見的格式）owner 在素材「審核紀錄」裡的決定（例如公開的名稱盡量少提）照做。

## 七條主線

影片不是程式碼的導讀，也不是設計決定的清單。**素材不是腳本的目錄**：素材寫得完整是為了查證和排除，
腳本只講編排挑出來的部分，大部分主張不會出現在影片裡。

1. **從使用的人想起。** 主軸是「需求 → 成果 → 怎麼做到」：先講誰、想做什麼、現在哪裡不方便，再讓觀眾看到它給了什麼，然後才講怎麼做到的。
   專案存在的理由不是它踩過的坑：**不拿技術事故開場，也不設「核心設計主張」的段落。**
2. **主次照專案的目的排，不照紀錄的多寡排。** 哪些主題是主體、哪些是配角，看素材「審核紀錄」裡 owner 的排序；沒有就在審核點一問（附預設）。
   文件裡寫得最詳細的那次事故，常常只是配角；主體是使用的人拿到的東西是怎麼做出來的。
3. **照故事線走，架構圖是地圖。** 一個專案通常同時做兩三件事（素材的故事線）。一條線從頭講到尾，才換下一條；
   換線時先講一句橋接，說這兩件事是什麼關係。**不可以因為圖上有另一條連線就跳過去講別的事。**
   每一個細節都掛在圖上的某個節點或某條連線上，並在旁白裡說出是哪一塊（「檢查器怎麼判定？」）。掛不上去的細節不放。
4. **每個主題都講到聽得懂它是怎麼做的。** 只說「遇到 A，所以改成 B」不算講了；B 實際怎麼運作要講出來。寫法見下面的「主題怎麼講」。
5. **背景先交代。** 專案的很多做法，是因為外部的服務或技術有某個行為（排程不保證準時、來源只保留最近幾筆）。
   觀眾不知道這件事，就聽不懂做法。素材的每條弧列了「需要的背景」：第一次用到時，在講做法之前用一到兩句交代。
6. **用真的例子。** 深講的主題至少有一個取自實際資料的例子（素材的實例）：真的一則貼文、真的一列資料、真的一行紀錄，從頭跟到尾。
   觀眾是靠例子看懂的。自己編的示意只在素材沒有實例時用，並標明「示意」。
7. **原文只是佐證。** `file`、`terminal`、`tree` 用來證明或示範前面剛講過的一句主張，不拿來開啟一個主題。
   一個主張最多配一到兩個。

### 主題怎麼講

每條故事線走完架構之後，講編排為它挑的幾個主題（素材的因果弧）。一個深講的主題用三到五個場景，照這個順序：

0. **背景**（這個主題需要、而且觀眾還沒聽過時）：外部的服務或技術本身怎麼運作，一到兩句，例如「代管的排程在尖峰時段會延後，甚至整輪不跑」。
   它是事實的交代：講完立刻接下去。數字要照背景知識寫的講；背景知識註明「不是官方來源」的，旁白不說成官方的說法。
1. **做什麼**：這一步收進什麼、交出什麼。**用一個實例帶**：這一則貼文進來，出去的時候變成什麼樣子。
2. **怎麼做**：機制。誰、對誰、做什麼、多久一次。畫出來，讓例子在圖上走一遍。
3. **卡在哪**：照直覺的做法會出什麼事。實際發生過就用那一次（事故放在這裡，不放在開場）。
4. **怎麼解**：現在的做法，同樣把機制講清楚：改了哪裡、現在一步一步怎麼走、出錯時怎麼知道。
   **解法的篇幅不少於問題。** 檢驗方式：觀眾聽完能不能向別人說出「所以它現在是怎麼運作的」。
   素材裡這個主題講做法的主張太少、講不到這個程度時，不要硬講：回 arch-material 補，或把它降成「帶過」。
5. **為什麼這樣解**：原因、考慮過沒採用的做法（用過去式）、換來什麼與代價。
6. **帶得走的**（可以省略）：一句換到別的專案也用得上的做法，放在這個主題的最後一句。結尾不再重複。

- 不必每一項都各佔一個場景。常見的排法：做什麼加怎麼做一到兩個場景（帶著實例），卡在哪一個場景，怎麼解一到兩個場景，為什麼併在怎麼解的最後。
  「卡在哪」和「怎麼解」最適合用同一張圖演兩次：同一個例子，照舊的做法走一次、照現在的做法走一次，讓觀眾看到差別。
- **主體的故事線講深一到三個主題；配角的故事線（排程、監控這類讓它持續運作的事）用一到兩個場景講完**，但「怎麼解」仍然要講完整，不能只留結論。
  編排為配角指定了更多內容時以編排為準，並在審核點二說明它用了幾個場景。
- 素材裡原因標成〔不明〕的做法：不講它的原因，也不把它的數值放上 `stat`。做法本身可以照常講。
- 弧的「口述」是 owner 親口說的原因，可以講，但照原話的意思講，不加油添醋。「缺口」裡標明是推斷的內容不當成事實講。
- 弧有「後續發展」時，照最新的狀態講；被推翻的做法只能當成「沒採用」的對照。
- 規則和限制用一正一反兩個例子講：一個它讓事情順利的情況，一個少了它會出事的情況。實例裡正反兩種都有時，兩個都用。

### 講到多深

- 旁白講**做什麼、為什麼、交給誰**，不講**怎麼寫的**。
- 觀眾看完要能說出每一塊的責任、資料怎麼流、幾個關鍵的決定和它們的原因；不需要能重寫程式。
- 函式名、變數名、參數列、行號不進旁白。檔名只在它本身就是使用者會碰到的東西時才提（例如設定檔、指令）。
- **數字不單獨出現。** 每個上畫面的數字，都要講它為什麼是這個值，或它造成什麼影響；講不出來就不放。（程式會檢查 `stat` 場景）
- **數字出現後，立刻換算成一個具體的情況。** 例如「每輪最多十則」之後接「一小時進來三十則，就要三輪才翻得完」。
  觀眾記得住的是情況，不是數字。
- 選項、旗標、錯誤碼不逐一列舉。挑最常用的一個示範，其餘一句話帶過或不講。
- 限制只講觀眾一用就會碰到的，最多三到四項。
- 出處（座標）只留在素材和審核點的表裡，不上畫面。

### 取捨的標準

每個場景問一次：**拿掉它，觀眾會少理解一塊，或少學到一件事嗎？** 不會就拿掉。
只報出一個事實、沒有原因也沒有影響的場景，先補上原因；補不出來就拿掉。

- 佐證類場景（`file`、`terminal`、`tree`）不超過場景總數的三分之一。（程式會檢查）
- 內容少就做短。小專案每一段都往下限取：開場兩到三個場景、成果一到兩個、架構兩個、主題兩到三個（每個三個場景上下）、結尾四個。
  不要為了把元件用齊而加場景。
  - 怎麼算小專案：使用者說它小，或只有一個使用情境、架構圖大約八個節點以內。拿不準就照小專案做，在審核點二說明還可以加什麼。
  - 取下限時可以合併的段落：痛點併進情境的最後一句；預告併進專案登場的畫面（用標籤）；
    帶走的話放在片尾卡上。骨架的順序不變。
- 估長度：一句旁白連同句間的停頓大約六秒，6 分鐘約 60 句。架構圖逐區講解加資料流追蹤，一區一句、一條連線一句，十個節點左右的圖大約要一分半鐘。

## 整支影片的骨架

影片分四段，順序固定。各段的比例是參考值，不是硬性規定。

**長度照編排定的目標長度**（沒指定時小專案 6 分鐘，見 `SKILL.md` 的編排步驟）。每個主題照骨架給場景，講完就停。
不為了湊長度加場景，也不為了壓長度省掉骨架裡的段落：要短就少講深一條弧。

### 1. 開場：使用情境（約 8%）

- **從使用的人講起，不從專案講起，也不從事故講起。** 順序：**誰 → 想做什麼 → 現在怎麼做、哪裡不方便 → 專案登場 → 接下來要講什麼**。
  - 用白話講一個具體的人和他的一天，例如「你追蹤幾個帳號，想知道他們今天發了什麼，又不想一直滑手機；貼文還是日文」。
    每一件事都要對得到素材的條目（主旨的第一段、講使用情境的事實）；素材沒有的情境不編，回 arch-material 補。
  - 畫面跟著情境選：手動重複的事用 `cycle`、`flow`；一段對話用 `chat`；數量與時間用 `layout` 的零件。不用清單條列痛點。
  - 登場：這時才放 `title`。預告用 `list`（`style: "number"`）列出接下來的幾段，或併進登場的畫面。
- 專案踩過的坑、出過的事故不放在開場：它們屬於某個主題的「卡在哪」。

### 2. 它給你什麼（約 8%）

- **先讓觀眾看到成果，再講怎麼做到。** 使用的人最後拿到什麼：畫面上有什麼、可以做什麼。
- **用實例**：素材裡真的一則資料，連同它被處理之後的樣子（例如一則貼文、它的翻譯、附的單字）。
  素材有這個實例在 app 上的截圖時，用 `shot` 放實際的畫面，框出旁白講到的那一塊；沒有截圖才用 `layout` 的 `panel`、`points` 畫，標題寫明是實際的資料。
- 這一段不講怎麼做到的。最後一句把問題丟出來（「這些是怎麼來的？」），接到架構圖。

### 3. 架構與主題（約 65%）

**架構圖只有一張，但不是把圖上的連線依序唸完。** 圖是地圖，故事線是路線：

1. （需要時才做）先交代有哪些東西。只有當「東西放在哪」本身是觀眾需要知道的事才用 `tree`，
   例如 skill 是由哪幾個檔案組成的。一般的程式專案直接從架構圖開始，不列原始碼檔案。
2. **全圖**（`map`）：放出整張圖，用一兩句說這個專案做哪幾件事，也就是有哪幾條故事線。
   可以在同一個場景逐區帶過（`focus` 的 `zone`），一區一句，只說這一區是什麼，不展開。
3. **每條故事線一章**。章內的順序：
   - **橋接句**（第一條故事線不用）：這條線和前一條是什麼關係，例如「貼文進了資料庫，同一輪接著做第二件事：翻譯」。
     它是這一章的第一句旁白。沒有它，觀眾會以為還在講上一件事。
   - **走這條線**：回到架構圖（`map`，`draw: false`），只追這條線經過的節點與連線（`focus` 的 `trace`、`nodes`），
     一條連線一句，說清楚「誰把什麼交給誰」。**別條故事線的連線這時不追。**
   - **講這條線的主題**（見「主題怎麼講」）。每個主題的第一句說出它掛在圖上的哪一塊。故事線的順序照主次與資料的流向排：主體在前，讓它持續運作的配角在後。
   - 章的最後一句收在這條線做到了什麼，不必是一句做法的總結。
4. **幾條故事線共用的部分**（同一個排程、同一張表）在第一次經過時講清楚；之後的故事線再經過，只用半句帶回（「還是同一個排程觸發」），不重講。

- 一條故事線在圖上走的那一段放在同一個 `map` 場景裡，鏡頭才不會跳；連線超過八條時拆成兩個相連的 `map` 場景（都用 `draw: false`）。
- 資料流的另一端不在圖上時（例如被呼叫的外部網站），沒有連線可以追：改用 `focus` 的 `nodes` 框住圖上和它往來的那個節點。
- 一章裡每講完兩個主題，下一個主題開頭回到架構圖一次（`map`，`draw: false`，鏡頭框住接下來要講的節點），觀眾才不會迷路。
- 講主題時優先用 `layout`、`flow`、`cycle` 把機制畫出來，`compare`、`statement` 用來下結論；`file`、`terminal` 只在需要看到原文或實際操作時才用，
  內容優先取素材的物證。
- **只有一條故事線的專案**：全圖之後逐區講解，再跟著資料把主要的連線走一遍，然後講主題。
- **使用者點名的額外功能，每一個各自成一章**，放在這一段的後面。每一章照同樣的順序講：
  它解決什麼、怎麼運作、怎麼用。開場的預告與結尾的使用情境都要涵蓋這些主題。
- **素材由好幾個子專案組成時**（好幾個 repo，或一個 repo 裡好幾個獨立的部分），影片要拆開講：
  1. 先用一張涵蓋全部的整體架構圖，講各部分怎麼分工、資料怎麼流。每個子專案在圖上是一區。
  2. 每個子專案各自成一章。章的開頭回到整體圖（`map`，`draw: false`，鏡頭框住它那一區），
     再照「它解決什麼、怎麼運作、關鍵的決定與原因」講。章的最後一句收在這個子專案做到了什麼。
  3. 最後回到整體收尾。預告、結尾的使用情境與適合不適合都要點到每個子專案。

### 4. 結尾：回到使用的人（約 10%，三個場景上下）

**不可以講完細節就直接結束，也不要用一張「做法回顧」的清單收尾。** 觀眾最後要知道的是：什麼情況下會用到它、它適不適合自己。依序交代：

1. **使用情境**：用白話講一到兩個具體的情況：誰、遇到什麼事、用了它之後變成怎樣（「你有一個公開的網站，想顯示翻譯好的貼文，又不想讓網站碰到付費的模型」）。
   不用術語、不提內部的元件名稱。情境裡的每一件事都要對得到素材的條目（主旨、現況事實、弧的所求）；素材沒有的情境不編。
   能畫就畫：用 `flow`、`chat` 或 `layout` 把那個情況演出來，不用清單。
2. **什麼時候適合用、什麼時候不適合**：用 `compare`。每一點是一個使用上的條件或限制，不是設計原則。
3. **一句收尾的話**（`statement`），最後是片尾卡（`title`，附專案網址；素材裡沒有公開的網址就不放）。
   網址裡有個人帳號時預設不放，在審核點二提出來，由使用者決定。

- 結尾的最後一句最好呼應開場的情境。
- 結尾不回顧「帶得走的做法」。各個決定的做法已經在講那個決定時說過了。
- **預設不講「怎麼開始」**（安裝步驟、要準備的帳號與金鑰）：大部分觀眾是來理解它怎麼運作的，不是來架一份。
  使用者要求、或這支影片本來就是教人上手時才加，放在適合與不適合之後；素材裡沒有指令的原文時畫步驟，不編指令。

## 場景的規則

- **一個場景只講一個概念。** 一個概念講不完就拆成兩個場景，不要在同一個畫面塞兩件事。
  例外是架構圖的逐區講解與資料流追蹤：它們是「走一遍架構」這一件事，放在同一個場景。
- **畫面比旁白先到。** 重要的元素都掛一個觸發詞（`at`）。程式會讓元素在旁白講到那個子句之前 0.8 秒出現，
  觀眾先看到、再聽到。寫分鏡時配合這件事：
  - 觸發詞挑「旁白第一次講到這個元素」的那個子句裡的詞，不要挑後面才出現的詞。
  - 卡片、視窗這類容器的標題如果會被唸出來，容器要在唸到標題之前出現（給容器自己的 `at`）。
  - 沒有觸發詞的元素會接在前一個元素後面出現；旁白很短時它可能來不及，寧可都掛觸發詞。
  - 元素排在場景的旁白講完之後才出現會警告。（程式會檢查）
- **場景開始後 1.5 秒內畫面要有東西。**（程式會檢查）旁白還在鋪陳時，先放小標或標題，不要讓畫面空著。
- **表現方式要有變化。**
  - 同一種元件不連續出現超過兩次。架構圖的全圖、逐區講解、資料流追蹤算同一件事，可以連續三個 `map`。
    `layout` 看它放的零件：零件的組合不同就算不同的畫面，相同的組合才算重複。
  - 一支三分鐘以上的影片至少用到六種元件；比這短的影片不用湊。
  - **純文字的場景不超過四成，也不連續超過兩個。**（程式會檢查）純文字指 `statement`、`compare`、`list`、`stat`，
    以及只放 `points`、`figure` 的 `layout`；`title` 不算。超過時，把講數量、時間、進度、狀態、流程的那幾個改用圖形來畫。
  - **每個決定至少有一個場景是用圖形講的。** 圖形本身要呈現機制：誰交給誰、多少裡面的多少、先後順序、狀態怎麼變。
    把一句話放大、或把三點條列出來，不算圖形。
  - **畫面裡的東西要會變。** 能隨旁白改變的就讓它變：格子一批一批填滿、計數往上數、清單裡的某一列從等待變成失敗。
    一進場就全部到齊、之後不動的畫面，只留給真的沒有過程可講的內容。
  - 內容適合哪種元件就用哪種：對話用 `chat`、兩相比較用 `compare`、數字用 `stat`、檔案結構用 `tree`、
    指令用 `terminal`、會重複的流程用 `cycle`、單向的流程用 `flow`、條列用 `list`、原文佐證用 `file`。
  - **數量、時間、進度要畫出來。**「一天該跑 24 次、實際只跑 9 次」「積了 300 則、每輪消化 10 則」「實測離上限多遠」
    這類內容用 `layout` 的零件（格子、時間格、長條）呈現，讓觀眾看到比例與變化；`stat` 只留給單獨一兩個、不需要比較的數字。
  - **兩相比較時，先看比的是什麼。** 比的是過程或數量（有上限與沒有上限各會怎樣），用 `layout` 左右兩格各放一個圖形零件，
    讓兩邊演出不同的結果；比的是特性（適合與不適合），才用 `compare` 條列。
  - **使用者在 app 上看得到的東西，用實際的畫面。** 素材有截圖（`data:screens/…`）就用 `shot`，旁白講到哪裡就框到哪裡；
    不要把畫面上本來就有的東西重畫成卡片。截圖只負責「長什麼樣子」，機制還是用圖形講。
  - **講到某個工具裡會看到的清單或紀錄**（執行紀錄、佇列、資料表的幾列），用 `layout` 的 `panel` 畫出來。
    圖的旁邊需要一兩句重點時，一格放圖、一格放 `points`。
  - **示意的內容要標明。** `panel` 的列、`slots` 亮哪幾格、`units` 的總數，如果是舉例而不是素材裡的實際紀錄，
    在標題或標籤寫上「示意」或「假設」，旁白也用「假設」「舉個例子」帶出來。數值本身仍然要對得到素材。

## 旁白

- **繁體中文，口語。** 寫出來要像對同事講話，不是唸文件。
- **用詞要指得出是哪一個東西。** 觀眾聽到一個名詞，要知道畫面上、架構圖上是哪一個。
  - **專有名詞第一次出現就介紹，之後改用白話。** 產品、服務、格式的名字（Supabase、RSS、GitHub Actions），觀眾多半沒聽過：
    第一次講到時，同一句或下一句用半句白話說它是什麼、在這個專案裡做什麼：「Supabase，一個雲端的資料庫服務，貼文都存在這裡」
    「RSS，一種讓閱讀器自動收到新文章的訂閱格式」。之後改用白話的代稱（「資料庫」「訂閱」），不再一直唸名字。
    代稱要在全片只指得到那一個東西：片中只有一個資料庫，就可以說「資料庫」；有兩個排程，就說「GitHub 內建的排程」「外部的排程」，
    不能只說「排程」。要和別的東西對比、或換了一章重新提起時，再說一次名字。
    介紹、代稱與出現的場景先寫在編排的「名詞」表（見 `treatment-format.md`），寫分鏡時照抄進 `meta.terms`。（程式會檢查）
  - 名字本身不可以換成籠統的詞：要指 GitHub Actions 時說「GitHub Actions」或介紹過的代稱，不說「平台」。
    產品與服務的名字不是素材「審核紀錄」裡要少提的那種公開名稱（那指的是人、團體、帳號）；名字列進 `meta.properNouns`。
  - 籠統的詞（平台、清單、來源、服務、系統、資料、東西、這一步、那條路）第一次出現時要說清楚是哪一個：
    「每個帳號在 rss.app 上的 RSS」「每一列多一個欄位，記下哪些帳號讀到過它」「頻道公開的直播播放清單」。之後同一個東西用同一個說法，不換成別的籠統詞。
  - 同一個詞在一支影片裡只指一種東西：前面「清單」指播放清單，後面就不要用「清單」指資料表的欄位。
  - 寫完拿全片的旁白與畫面文字找一次這些詞，每一處都問：觀眾知道是哪一個嗎？
- **因果講明白。** 有推理的句子直接用「因為…所以…」「為了…」「不然…」「這樣一來…」講出來，
  不要把原因藏成名詞（「基於穩定性的考量」）或只留結論。（程式會數帶有這類連接詞的句子，太少會警告）
  - 只用在真的有推理的句子。單純描述畫面或交代順序的句子不要硬套。
  - 連接詞輪流用，同一個詞不要連續用兩次。
- **術語第一次出現時，用半句白話說它是什麼。** 「邊緣快取，也就是離使用者最近的那一層暫存」。專有名詞的做法見上面「用詞要指得出是哪一個東西」。
- **比喻從日常經驗來，用平實的話講。**
  - 一章最多一個比喻，在那一章裡用同一套說法；不跨章延續。
  - 比喻之後要接回真實的機制（「換成程式的說法，就是…」），不可以只留比喻。
  - 不演戲：不把元件擬人成角色，不用打仗、比賽、輸贏的說法。
  - 不必每一章都有比喻。找不到貼切的就直接講。
- **只保留專有名詞的英文，其餘用中文說。**（程式會檢查）
  - 專有名詞指專案、產品、工具的名稱，例如 arch-blueprint、Claude Code。把它們列在分鏡的 `meta.properNouns`。
  - 其他英文詞（一般術語、檔名）在 `say` 欄位改成中文說法。中文配音唸英文詞的語調不自然。
  - 沒有自然中文說法的格式或協定名稱（例如 Markdown、JSON、HTTP）可以列進 `meta.properNouns` 照唸。
  - 指令的選項不唸出原文，用它的作用來說（「加上輸出成 JSON 的選項」）；原文放在畫面上。
  - 字幕可以保留英文原詞：`text` 是字幕，`say` 是實際唸出來的話。沒有 `say` 時兩者相同。
  - 同一個詞在整支影片裡用同一個中文說法。目前用過的：

    | 字幕顯示 | 旁白唸 |
    |---|---|
    | skill | 技能 |
    | SKILL.md | 技能說明檔 |
    | README | 專案說明 |
    | SVG | 向量圖 |

- **一句旁白就是一行字幕，不超過 30 個全形字寬。**（程式會檢查）太長就拆成兩句。編排裡的橋接句超過時，照原文拆成幾行，不改用字。
- **觸發詞要出現在實際唸出來的話裡。**（程式會檢查，找不到會報錯）
  有 `say` 的句子，觸發詞要從 `say` 裡挑，不是從 `text`。

## 畫面上的字

- **藍圖地圖裡的字是英文。** 這是 arch-blueprint 的規則，圖直接拿來用，不改。
  旁白在 `map` 場景講到圖上的分區或節點時，字幕（`text`）用圖上的英文名稱，唸法（`say`）用中文；其他場景的字幕直接用中文。整支影片同一個名稱用同一個說法。
- **標語、註解、流程步驟的名稱用繁體中文**，和旁白一致。
- **每個元件都有字數上限。**（程式會檢查）超過會警告或截斷，各元件的上限見 `storyboard-format.md`。

## 顏色

- **強調色（`accent`）只用來標示「現在正在講的東西」。**
- **第二強調色（`accent2`）只在需要和強調色區分時使用**，例如流程裡性質不同的步驟。
  一個畫面裡不要讓兩個強調色同時搶眼。

## 轉場

轉場代表兩個場景之間的關係，不是裝飾。

| 兩個場景的關係 | 轉場 |
|---|---|
| 換章節 | `wipe`。程式會自動輪流用三種樣式（橫條、圓形、直條），不用自己指定 |
| 同一章的下一個重點 | `push`（往左推） |
| 從主張進到佐證、從概念進到數字或細節 | `push-up`（往上推） |
| 拉近看細節 | `zoom` |
| 同一張架構圖接著講 | `cut`（預設） |

同一種轉場不要連續用三次以上。
小專案每章只有一個場景時，會連續換章節：這時中間那一次改用 `zoom`（例如專案登場），不要三個 `wipe` 連在一起。
