# 腳本規則

寫旁白與分鏡時遵守。標「程式會檢查」的規則，違反時 `arch-video build` 會報錯或警告；
其餘靠寫的人自己把關。

**內容的來源是內容大綱（`brief.md`）**，整理方式見 `source-rules.md`。三條底線：

- 講到功能或行為的旁白，都對得到大綱裡的編號；開場的情境例子與串場的句子除外。
- 還沒實裝或打算做的功能完全不提，包括結尾。可以講現在的行為與限制。
- 機密與個資不進旁白、不進畫面。（程式會檢查常見的格式）

## 三條主線

影片不是程式碼的導讀。**大綱是素材庫，不是腳本的目錄**：大綱寫得完整是為了對齊和排除，
腳本只從裡面挑出服務故事的部分，大部分事實不會出現在影片裡。

1. **從需求想起。** 觀眾先知道「為什麼需要它」，才聽「它是什麼」。開場用大綱的「為什麼需要它」寫。
2. **架構圖帶著走。** 主體是那張架構圖：有哪幾塊、各自負責什麼、資料怎麼流。
   架構圖講完之後補的每一個細節，都要掛在圖上的某個節點或某條連線上，並在旁白裡說出是哪一塊
   （「檢查器怎麼判定？」）。掛不上去的細節不放。
3. **範例只是佐證。** `file`、`terminal`、`tree` 用來證明或示範前面剛講過的一句主張，不拿來開啟一個主題。
   一個主張最多配一到兩個範例。

### 講到多深

- 旁白講**做什麼、為什麼、交給誰**，不講**怎麼寫的**。
- 觀眾看完要能說出每一塊的責任、資料怎麼流、怎麼開始用；不需要能重寫程式。
- 函式名、變數名、參數列、行號不進旁白。檔名只在它本身就是使用者會碰到的東西時才提（例如設定檔、指令）。
- 數字只留會改變觀眾怎麼用它的那幾個（上限、預設值）。其餘留在大綱裡。
- 選項、旗標、錯誤碼不逐一列舉。挑最常用的一個示範，其餘一句話帶過或不講。
- 限制只講觀眾一用就會碰到的，最多三到四項。
- 出處（路徑與行號）只留在大綱和審核點的表裡，不上畫面。

### 取捨的標準

每個場景問一次：**拿掉它，觀眾對「為什麼需要、架構長怎樣、怎麼用」的理解會少一塊嗎？** 不會就拿掉。

- 佐證類場景（`file`、`terminal`、`tree`）不超過場景總數的三分之一。（程式會檢查）
- 內容少就做短。小專案每一段都往下限取：開場三個場景、核心想法一個、架構兩個加一到兩個細節、結尾四個。
  不要為了把元件用齊而加場景。
  - 怎麼算小專案：使用者說它小，或只有一個使用情境、架構圖大約八個節點以內。拿不準就照小專案做，在審核點二說明還可以加什麼。
  - 取下限時可以合併的段落：痛點併進情境的最後一句；預告併進專案登場的畫面（用標籤）；
    帶走的話放在片尾卡上。骨架的順序不變。
- 估長度：一句旁白連同句間的停頓大約五秒。架構圖逐區講解加資料流追蹤通常要一分鐘左右。

## 整支影片的骨架

影片分四段，順序固定。各段的比例是參考值，不是硬性規定。

**長度沒有預設值，由內容決定。** 先列出要講的主題（專案本身，加上使用者點名的額外功能），
每個主題照骨架給足場景，講完就停。不為了湊長度加場景，也不為了壓長度省掉骨架裡的段落。

### 1. 開場：從需求出發（約 15%）

- **不要一開始就介紹專案。** 先讓觀眾想起自己遇過的問題，再讓專案以「答案」的身分登場。
- 順序：**情境 → 痛點 → 「如果…呢？」→ 專案登場 → 接下來要講什麼**。
  - 情境：一個具體的時刻，用 `chat` 最合適（誰問了什麼、你怎麼回）。
  - 痛點：現有做法哪裡不好，用 `compare` 或 `list`。
  - 提問：一句「如果…呢？」，用 `statement`。
  - 登場：這時才放 `title`。
  - 預告：用 `list`（`style: "number"`）列出接下來的幾段。
- 情境可以是虛構的例子，但要用「想像一下」「假設」這類說法標明，而且痛點要對得上專案實際解決的事。

### 2. 核心想法（約 10%）

- 專案最重要的一兩句主張，用 `statement`；有關鍵數字就用 `stat`。

### 3. 架構與細節（約 55%）

- **架構圖是主角，要花足夠的篇幅講。** 依序做這幾件事：
  1. （需要時才做）先交代有哪些東西。只有當「東西放在哪」本身是觀眾需要知道的事才用 `tree`，
     例如 skill 是由哪幾個檔案組成的。一般的程式專案直接從架構圖開始，不列原始碼檔案。
  2. 放出架構圖全圖（`map`）。
  3. **逐區講解**：一句旁白講一區，鏡頭拉近那一區（`focus` 的 `zone`），說出區裡有哪些節點、各自負責什麼。
  4. **跟著資料走一遍**：一句旁白講一條連線（`focus` 的 `trace`），說清楚「誰把什麼交給誰」。主要的連線每一條都要走到。
     資料流的另一端不在圖上時（例如被呼叫的外部網站），沒有連線可以追：改用 `focus` 的 `nodes` 框住圖上和它往來的那個節點。
- 逐區講解與資料流追蹤放在同一個 `map` 場景裡（`draw: false`，接在全圖場景之後），鏡頭才不會跳。
- 架構講完，再補充規則、用法與流程的細節。每個細節掛在圖上的一個節點或一條連線上，先講主張，再用範例佐證。
  優先用 `flow`、`cycle`、`compare`、`stat`、`statement` 把概念講清楚；`file`、`terminal` 只在需要看到原文或實際操作時才用。
- 細節講了三個場景以上，中間回到架構圖一次（`map`，`draw: false`，鏡頭框住接下來要講的節點），觀眾才不會迷路。
- **使用者點名的額外功能，每一個各自成一章**，放在這一段的後面。每一章照同樣的順序講：
  它解決什麼、怎麼運作、怎麼用。開場的預告與結尾的回顧都要涵蓋這些主題。

### 4. 結尾：完整收束（約 20%，至少四個場景）

- **不可以講完細節就直接結束。** 依序交代：
  1. **重點回顧**：三到四點，用 `list`（`style: "check"`）。
  2. **什麼時候適合用、什麼時候不適合**：用 `compare`。
  3. **怎麼開始**：實際的一句話或一行指令，用 `chat` 或 `terminal`。
  4. **一句讓人帶走的話**（`statement`），最後是片尾卡（`title`，附專案網址；素材裡沒有公開的網址就不放）。
- 結尾的最後一句最好呼應開場的情境。

## 場景的規則

- **一個場景只講一個概念。** 一個概念講不完就拆成兩個場景，不要在同一個畫面塞兩件事。
  例外是架構圖的逐區講解與資料流追蹤：它們是「走一遍架構」這一件事，放在同一個場景。
- **畫面比旁白先到。** 重要的元素都掛一個觸發詞（`at`）。程式會讓元素在旁白講到那個子句之前 0.8 秒出現，
  觀眾先看到、再聽到。寫分鏡時配合這件事：
  - 觸發詞挑「旁白第一次講到這個元素」的那個子句裡的詞，不要挑後面才出現的詞。
  - 卡片、視窗這類容器的標題如果會被唸出來，容器要在唸到標題之前出現（給容器自己的 `at`）。
  - 沒有觸發詞的元素會接在前一個元素後面出現；旁白很短時它可能來不及，寧可都掛觸發詞。
  - 元素排在場景的旁白講完之後才出現會警告。（程式會檢查）
- **場景開始後 1.5 秒內畫面要有東西。**（程式會檢查）旁白還在鋪陳時，先放小標或標題，不要讓畫面空著。
- **表現方式要有變化。**
  - 同一種元件不連續出現超過兩次。
  - 一支三分鐘以上的影片至少用到六種元件；比這短的影片不用湊。
  - 內容適合哪種元件就用哪種：對話用 `chat`、兩相比較用 `compare`、數字用 `stat`、檔案結構用 `tree`、
    指令用 `terminal`、會重複的流程用 `cycle`、單向的流程用 `flow`、條列用 `list`、原文佐證用 `file`。

## 旁白

- **繁體中文，口語。** 寫出來要像對同事講話，不是唸文件。
- **只保留專有名詞的英文，其餘用中文說。**（程式會檢查）
  - 專有名詞指專案、產品、工具的名稱，例如 arch-blueprint、Claude Code。把它們列在分鏡的 `meta.properNouns`。
  - 其他英文詞（一般術語、檔名）在 `say` 欄位改成中文說法。中文配音唸英文詞的語調不自然。
  - 沒有自然中文說法的格式或協定名稱（例如 Markdown、JSON、HTTP）可以列進 `meta.properNouns` 照唸。
  - 指令的選項不唸出原文，用它的作用來說（「加上輸出成 JSON 的選項」）；原文放在畫面上。
  - 字幕可以保留英文原詞：`text` 是字幕，`say` 是實際唸出來的話。沒有 `say` 時兩者相同。
  - 同一個詞在整支影片裡用同一個中文說法。目前用過的：

    | 字幕顯示 | 旁白唸 |
    |---|---|
    | skill | 技能 |
    | SKILL.md | 技能說明檔 |
    | README | 專案說明 |
    | SVG | 向量圖 |

- **一句旁白就是一行字幕，不超過 30 個全形字寬。**（程式會檢查）太長就拆成兩句。
- **觸發詞要出現在實際唸出來的話裡。**（程式會檢查，找不到會報錯）
  有 `say` 的句子，觸發詞要從 `say` 裡挑，不是從 `text`。

## 畫面上的字

- **藍圖地圖裡的字是英文。** 這是 arch-blueprint 的規則，圖直接拿來用，不改。
  旁白講到圖上的分區或節點時，字幕（`text`）用圖上的英文名稱，唸法（`say`）用中文，整支影片同一個名稱用同一個說法。
- **標語、註解、流程步驟的名稱用繁體中文**，和旁白一致。
- **每個元件都有字數上限。**（程式會檢查）超過會警告或截斷，各元件的上限見 `storyboard-format.md`。

## 顏色

- **強調色（`accent`）只用來標示「現在正在講的東西」。**
- **第二強調色（`accent2`）只在需要和強調色區分時使用**，例如流程裡性質不同的步驟。
  一個畫面裡不要讓兩個強調色同時搶眼。

## 轉場

轉場代表兩個場景之間的關係，不是裝飾。

| 兩個場景的關係 | 轉場 |
|---|---|
| 換章節 | `wipe`。程式會自動輪流用三種樣式（橫條、圓形、直條），不用自己指定 |
| 同一章的下一個重點 | `push`（往左推） |
| 從主張進到佐證、從概念進到數字或細節 | `push-up`（往上推） |
| 拉近看細節 | `zoom` |
| 同一張架構圖接著講 | `cut`（預設） |

同一種轉場不要連續用三次以上。
