# 腳本規則

寫旁白與分鏡時遵守。標「程式會檢查」的規則，違反時 `arch-video build` 會報錯或警告；
其餘靠寫的人自己把關。

**觀眾是沒碰過這個專案的工程師。** 他們看完要帶得走兩樣東西：這個專案現在怎麼運作，
以及**為什麼這樣設計**：當初遇到什麼問題、怎麼選、換來什麼、付出什麼。
只報告「有哪些流程、數值是多少」的影片，觀眾學不到東西，算是沒做好。

**內容的來源是內容大綱（`brief.md`）**，整理方式見 `source-rules.md`。四條底線：

- 講到功能或行為的旁白，都對得到大綱裡的編號；開場的情境例子與串場的句子除外。
- 講到原因的旁白，都對得到大綱裡一條有出處的原因。**查不到原因就不講原因，不可以自己編。**
- 還沒實裝或打算做的功能完全不提，包括結尾。可以講現在的行為與限制，也可以講當初考慮過、沒採用的做法（見「決定怎麼講」）。
- 機密與個資不進旁白、不進畫面。（程式會檢查常見的格式）

## 四條主線

影片不是程式碼的導讀。**大綱是素材庫，不是腳本的目錄**：大綱寫得完整是為了對齊和排除，
腳本只從裡面挑出服務故事的部分，大部分事實不會出現在影片裡。

1. **從需求想起。** 觀眾先知道「為什麼需要它」，才聽「它是什麼」。開場用大綱的「為什麼需要它」寫。
2. **架構圖帶著走。** 主體是那張架構圖：有哪幾塊、各自負責什麼、資料怎麼流。
   架構圖講完之後補的每一個細節，都要掛在圖上的某個節點或某條連線上，並在旁白裡說出是哪一塊
   （「檢查器怎麼判定？」）。掛不上去的細節不放。
3. **細節以「決定」為單位，每個決定都講原因與影響。** 不是一條一條報功能和設定值。寫法見下面的「決定怎麼講」。
4. **範例只是佐證。** `file`、`terminal`、`tree` 用來證明或示範前面剛講過的一句主張，不拿來開啟一個主題。
   一個主張最多配一到兩個範例。

### 決定怎麼講

架構圖講完之後的主體，由大綱「決策」那一節的條目組成。一個決定用兩到四個場景，照這個順序講：

1. **所求**：這裡要解決什麼問題，或卡在什麼兩難。先講需求，再講做法；觀眾要先知道為什麼需要這個東西。
2. **選擇**：現在的做法，連同關鍵的數值。
3. **因為**：為什麼這樣選。這一句是整個決定的重點，強調色放在這裡。
4. **不然**：不這樣做會怎樣。用反例，或是當初考慮過、沒採用的做法（用過去式講它為什麼沒被採用，不把它講成功能）。
5. **影響**：換來什麼、代價是什麼、碰到邊界時會發生什麼事。
6. **帶得走的**：一句換到別的專案也用得上的做法。可以放在這個決定的最後一句，或留到章末、結尾。

- 不必每一項都各佔一個場景。常見的排法：所求加選擇一個場景，因為加不然一個場景，影響一個場景。
  「不然」最適合用畫面演：`layout` 左右兩格，一邊是現在的做法、一邊是沒這樣做的結果，讓觀眾看到差別。
- **每一章挑兩到三個最有收穫的決定講深，其餘不講。** 寧可少講幾個，不要每個都只講到「選擇」就停。
- 大綱裡原因標成「不明」的決定：不講它的原因，也不把它當成一個決定來講、不把它的數值放上 `stat`。
  描述運作時少不了的數值（例如「每小時跑一次」）可以在講流程時順帶提到。
- 規則和限制用一正一反兩個例子講：一個它讓事情順利的情況，一個少了它會出事的情況。

### 講到多深

- 旁白講**做什麼、為什麼、交給誰**，不講**怎麼寫的**。
- 觀眾看完要能說出每一塊的責任、資料怎麼流、幾個關鍵的決定和它們的原因；不需要能重寫程式。
- 函式名、變數名、參數列、行號不進旁白。檔名只在它本身就是使用者會碰到的東西時才提（例如設定檔、指令）。
- **數字不單獨出現。** 每個上畫面的數字，都要講它為什麼是這個值，或它造成什麼影響；講不出來就不放。（程式會檢查 `stat` 場景）
- **數字出現後，立刻換算成一個具體的情況。** 例如「每輪最多十則」之後接「一小時進來三十則，就要三輪才翻得完」。
  觀眾記得住的是情況，不是數字。
- 選項、旗標、錯誤碼不逐一列舉。挑最常用的一個示範，其餘一句話帶過或不講。
- 限制只講觀眾一用就會碰到的，最多三到四項。
- 出處（路徑與行號）只留在大綱和審核點的表裡，不上畫面。

### 取捨的標準

每個場景問一次：**拿掉它，觀眾會少理解一塊，或少學到一件事嗎？** 不會就拿掉。
只報出一個事實、沒有原因也沒有影響的場景，先補上原因；補不出來就拿掉。

- 佐證類場景（`file`、`terminal`、`tree`）不超過場景總數的三分之一。（程式會檢查）
- 內容少就做短。小專案每一段都往下限取：開場三個場景、核心想法一到兩個、架構兩個、決定兩到三個（每個兩到三個場景）、結尾四個。
  不要為了把元件用齊而加場景。
  - 怎麼算小專案：使用者說它小，或只有一個使用情境、架構圖大約八個節點以內。拿不準就照小專案做，在審核點二說明還可以加什麼。
  - 取下限時可以合併的段落：痛點併進情境的最後一句；預告併進專案登場的畫面（用標籤）；
    帶走的話放在片尾卡上。骨架的順序不變。
- 估長度：一句旁白連同句間的停頓大約六秒。架構圖逐區講解加資料流追蹤，一區一句、一條連線一句，十個節點左右的圖大約要一分半鐘。

## 整支影片的骨架

影片分四段，順序固定。各段的比例是參考值，不是硬性規定。

**長度沒有預設值，由內容決定。** 先列出要講的主題（專案本身，加上使用者點名的額外功能），
每個主題照骨架給足場景，講完就停。不為了湊長度加場景，也不為了壓長度省掉骨架裡的段落。

### 1. 開場：從需求出發（約 15%）

- **不要一開始就介紹專案。** 先讓觀眾想起自己遇過的問題，再讓專案以「答案」的身分登場。
- 順序：**情境 → 痛點 → 「如果…呢？」→ 專案登場 → 接下來要講什麼**。
  - 情境：一個具體的時刻。**形式跟著痛點選，不要每支影片都用對話開場。** 第一個畫面要讓觀眾看到問題，不是讀到問題：

    | 這個專案的痛點是 | 開場的畫面 |
    |---|---|
    | 有人問了一個答不出來、或很費工才答得出來的問題 | `chat`：誰問了什麼、你怎麼回 |
    | 出過一次事（停擺、漏資料、花費暴增），專案是為了不再發生 | `layout`：用 `slots`、`panel`、`units` 把那一次畫出來 |
    | 同一件事要手動重複很多次 | `cycle`、`flow`，或 `layout` 的 `steps` 配上次數 |
    | 現有的工具卡在某一步 | `terminal`，或 `layout` 的 `term`、`panel`，示範卡住的那一刻 |

    大綱裡有實際發生過的事（有出處），優先用它開場；它比虛構的對話有說服力。它可能記在「為什麼需要它」，也可能記在某個決定的「影響」裡。
    拿某個決定的事故開場時，開場只演發生了什麼；原因和後來的做法留到講那個決定時再說，並回扣開場，不重講一次。
  - 痛點：現有做法哪裡不好，用 `compare` 或 `list`；情境的畫面已經把痛點演出來時，併成同一個場景。
  - 提問：一句「如果…呢？」，用 `statement`。
  - 登場：這時才放 `title`。
  - 預告：用 `list`（`style: "number"`）列出接下來的幾段。
- 情境可以是虛構的例子，但要用「想像一下」「假設」這類說法標明，而且痛點要對得上專案實際解決的事。

### 2. 核心想法（約 10%）

- 專案最重要的一個設計主張，用 `statement`，接著講它的原因：為什麼這樣設計，不這樣會怎樣。
  有關鍵數字就說明它代表的意義：單獨一個數字用 `stat`，要和別的量比較時用 `layout` 畫出來。

### 3. 架構與細節（約 55%）

- **架構圖是主角，要花足夠的篇幅講。** 依序做這幾件事：
  1. （需要時才做）先交代有哪些東西。只有當「東西放在哪」本身是觀眾需要知道的事才用 `tree`，
     例如 skill 是由哪幾個檔案組成的。一般的程式專案直接從架構圖開始，不列原始碼檔案。
  2. 放出架構圖全圖（`map`）。
  3. **逐區講解**：一句旁白講一區，鏡頭拉近那一區（`focus` 的 `zone`），說出區裡有哪些節點、各自負責什麼。
  4. **跟著資料走一遍**：一句旁白講一條連線（`focus` 的 `trace`），說清楚「誰把什麼交給誰」。主要的連線每一條都要走到。
     資料流的另一端不在圖上時（例如被呼叫的外部網站），沒有連線可以追：改用 `focus` 的 `nodes` 框住圖上和它往來的那個節點。
- 逐區講解與資料流追蹤放在同一個 `map` 場景裡（`draw: false`，接在全圖場景之後），鏡頭才不會跳。
  連線超過八條時可以拆成兩個相連的 `map` 場景（都用 `draw: false`）：一個逐區講解，一個追資料流。
- 架構講完，接著講決定（見「決定怎麼講」）。每個決定掛在圖上的一個節點或一條連線上，先講所求與主張，再用範例佐證。
  優先用 `layout`、`flow`、`cycle` 把機制畫出來，`compare`、`statement` 用來下結論；`file`、`terminal` 只在需要看到原文或實際操作時才用。
- 每個決定的第一句說出它掛在圖上的哪一塊。架構圖走完之後算起，每講完兩個決定，下一個決定開頭回到架構圖一次
  （`map`，`draw: false`，鏡頭框住接下來要講的節點），觀眾才不會迷路。
- **使用者點名的額外功能，每一個各自成一章**，放在這一段的後面。每一章照同樣的順序講：
  它解決什麼、怎麼運作、怎麼用。開場的預告與結尾的回顧都要涵蓋這些主題。
- **素材由好幾個子專案組成時**（好幾個 repo，或一個 repo 裡好幾個獨立的部分），影片要拆開講：
  1. 先用一張涵蓋全部的整體架構圖，講各部分怎麼分工、資料怎麼流。每個子專案在圖上是一區。
  2. 每個子專案各自成一章。章的開頭回到整體圖（`map`，`draw: false`，鏡頭框住它那一區），
     再照「它解決什麼、怎麼運作、關鍵的決定與原因」講。章的最後一句是這一章帶得走的做法。
  3. 最後回到整體收尾。預告、回顧、「怎麼開始」都要點到每個子專案。

### 4. 結尾：完整收束（約 20%，至少四個場景）

- **不可以講完細節就直接結束。** 依序交代：
  1. **帶得走的做法**：三到四點，用 `list`（`style: "check"`）。每一點是一個換到別的專案也用得上的做法，
     連同它的原因（「排程交給外部呼叫，因為內建的不保證準時」），不是功能清單。
  2. **什麼時候適合用、什麼時候不適合**：用 `compare`。
  3. **怎麼開始**：實際的一句話或一行指令，用 `chat` 或 `terminal`。大綱裡沒有指令的原文時不要編指令：
     改用 `flow` 或 `layout` 的 `steps` 畫出步驟。
  4. **一句讓人帶走的話**（`statement`），最後是片尾卡（`title`，附專案網址；素材裡沒有公開的網址就不放）。
     網址裡有個人帳號時預設不放，在審核點二提出來，由使用者決定。
- 結尾的最後一句最好呼應開場的情境。

## 場景的規則

- **一個場景只講一個概念。** 一個概念講不完就拆成兩個場景，不要在同一個畫面塞兩件事。
  例外是架構圖的逐區講解與資料流追蹤：它們是「走一遍架構」這一件事，放在同一個場景。
- **畫面比旁白先到。** 重要的元素都掛一個觸發詞（`at`）。程式會讓元素在旁白講到那個子句之前 0.8 秒出現，
  觀眾先看到、再聽到。寫分鏡時配合這件事：
  - 觸發詞挑「旁白第一次講到這個元素」的那個子句裡的詞，不要挑後面才出現的詞。
  - 卡片、視窗這類容器的標題如果會被唸出來，容器要在唸到標題之前出現（給容器自己的 `at`）。
  - 沒有觸發詞的元素會接在前一個元素後面出現；旁白很短時它可能來不及，寧可都掛觸發詞。
  - 元素排在場景的旁白講完之後才出現會警告。（程式會檢查）
- **場景開始後 1.5 秒內畫面要有東西。**（程式會檢查）旁白還在鋪陳時，先放小標或標題，不要讓畫面空著。
- **表現方式要有變化。**
  - 同一種元件不連續出現超過兩次。架構圖的全圖、逐區講解、資料流追蹤算同一件事，可以連續三個 `map`。
    `layout` 看它放的零件：零件的組合不同就算不同的畫面，相同的組合才算重複。
  - 一支三分鐘以上的影片至少用到六種元件；比這短的影片不用湊。
  - **純文字的場景不超過四成，也不連續超過兩個。**（程式會檢查）純文字指 `statement`、`compare`、`list`、`stat`，
    以及只放 `points`、`figure` 的 `layout`；`title` 不算。超過時，把講數量、時間、進度、狀態、流程的那幾個改用圖形來畫。
  - **每個決定至少有一個場景是用圖形講的。** 圖形本身要呈現機制：誰交給誰、多少裡面的多少、先後順序、狀態怎麼變。
    把一句話放大、或把三點條列出來，不算圖形。
  - **畫面裡的東西要會變。** 能隨旁白改變的就讓它變：格子一批一批填滿、計數往上數、清單裡的某一列從等待變成失敗。
    一進場就全部到齊、之後不動的畫面，只留給真的沒有過程可講的內容。
  - 內容適合哪種元件就用哪種：對話用 `chat`、兩相比較用 `compare`、數字用 `stat`、檔案結構用 `tree`、
    指令用 `terminal`、會重複的流程用 `cycle`、單向的流程用 `flow`、條列用 `list`、原文佐證用 `file`。
  - **數量、時間、進度要畫出來。**「一天該跑 24 次、實際只跑 9 次」「積了 300 則、每輪消化 10 則」「實測離上限多遠」
    這類內容用 `layout` 的零件（格子、時間格、長條）呈現，讓觀眾看到比例與變化；`stat` 只留給單獨一兩個、不需要比較的數字。
  - **兩相比較時，先看比的是什麼。** 比的是過程或數量（有上限與沒有上限各會怎樣），用 `layout` 左右兩格各放一個圖形零件，
    讓兩邊演出不同的結果；比的是特性（適合與不適合），才用 `compare` 條列。
  - **講到某個工具裡會看到的清單或紀錄**（執行紀錄、佇列、資料表的幾列），用 `layout` 的 `panel` 畫出來。
    圖的旁邊需要一兩句重點時，一格放圖、一格放 `points`。
  - **示意的內容要標明。** `panel` 的列、`slots` 亮哪幾格、`units` 的總數，如果是舉例而不是素材裡的實際紀錄，
    在標題或標籤寫上「示意」或「假設」，旁白也用「假設」「舉個例子」帶出來。數值本身仍然要對得到大綱。

## 旁白

- **繁體中文，口語。** 寫出來要像對同事講話，不是唸文件。
- **因果講明白。** 有推理的句子直接用「因為…所以…」「為了…」「不然…」「這樣一來…」講出來，
  不要把原因藏成名詞（「基於穩定性的考量」）或只留結論。（程式會數帶有這類連接詞的句子，太少會警告）
  - 只用在真的有推理的句子。單純描述畫面或交代順序的句子不要硬套。
  - 連接詞輪流用，同一個詞不要連續用兩次。
- **術語第一次出現時，用半句白話說它是什麼。** 「邊緣快取，也就是離使用者最近的那一層暫存」。之後才用裸的術語。
- **比喻從日常經驗來，用平實的話講。**
  - 一章最多一個比喻，在那一章裡用同一套說法；不跨章延續。
  - 比喻之後要接回真實的機制（「換成程式的說法，就是…」），不可以只留比喻。
  - 不演戲：不把元件擬人成角色，不用打仗、比賽、輸贏的說法。
  - 不必每一章都有比喻。找不到貼切的就直接講。
- **只保留專有名詞的英文，其餘用中文說。**（程式會檢查）
  - 專有名詞指專案、產品、工具的名稱，例如 arch-blueprint、Claude Code。把它們列在分鏡的 `meta.properNouns`。
  - 其他英文詞（一般術語、檔名）在 `say` 欄位改成中文說法。中文配音唸英文詞的語調不自然。
  - 沒有自然中文說法的格式或協定名稱（例如 Markdown、JSON、HTTP）可以列進 `meta.properNouns` 照唸。
  - 指令的選項不唸出原文，用它的作用來說（「加上輸出成 JSON 的選項」）；原文放在畫面上。
  - 字幕可以保留英文原詞：`text` 是字幕，`say` 是實際唸出來的話。沒有 `say` 時兩者相同。
  - 同一個詞在整支影片裡用同一個中文說法。目前用過的：

    | 字幕顯示 | 旁白唸 |
    |---|---|
    | skill | 技能 |
    | SKILL.md | 技能說明檔 |
    | README | 專案說明 |
    | SVG | 向量圖 |

- **一句旁白就是一行字幕，不超過 30 個全形字寬。**（程式會檢查）太長就拆成兩句。
- **觸發詞要出現在實際唸出來的話裡。**（程式會檢查，找不到會報錯）
  有 `say` 的句子，觸發詞要從 `say` 裡挑，不是從 `text`。

## 畫面上的字

- **藍圖地圖裡的字是英文。** 這是 arch-blueprint 的規則，圖直接拿來用，不改。
  旁白講到圖上的分區或節點時，字幕（`text`）用圖上的英文名稱，唸法（`say`）用中文，整支影片同一個名稱用同一個說法。
- **標語、註解、流程步驟的名稱用繁體中文**，和旁白一致。
- **每個元件都有字數上限。**（程式會檢查）超過會警告或截斷，各元件的上限見 `storyboard-format.md`。

## 顏色

- **強調色（`accent`）只用來標示「現在正在講的東西」。**
- **第二強調色（`accent2`）只在需要和強調色區分時使用**，例如流程裡性質不同的步驟。
  一個畫面裡不要讓兩個強調色同時搶眼。

## 轉場

轉場代表兩個場景之間的關係，不是裝飾。

| 兩個場景的關係 | 轉場 |
|---|---|
| 換章節 | `wipe`。程式會自動輪流用三種樣式（橫條、圓形、直條），不用自己指定 |
| 同一章的下一個重點 | `push`（往左推） |
| 從主張進到佐證、從概念進到數字或細節 | `push-up`（往上推） |
| 拉近看細節 | `zoom` |
| 同一張架構圖接著講 | `cut`（預設） |

同一種轉場不要連續用三次以上。
小專案每章只有一個場景時，會連續換章節：這時中間那一次改用 `zoom`（例如專案登場），不要三個 `wipe` 連在一起。
