# arch-video — 把專案素材變成架構解說影片

讀使用者給的素材，整理成內容大綱，寫出旁白與分鏡，產出一支有旁白、字幕、章節的 1080p 影片。
觀眾是沒碰過這個專案的工程師。看完要帶得走兩樣東西：**它現在怎麼運作**，以及**為什麼這樣設計**。
只報告流程和設定值的影片，觀眾學不到東西。

核心精神：

- **從需求想起，架構圖帶著走，範例只是佐證。** 影片不是程式碼的導讀：講做什麼、為什麼、交給誰，不講怎麼寫的。
- **每個決定都講原因與影響。** 當初遇到什麼問題、怎麼選、不這樣會怎樣、換來什麼、付出什麼。
  數字和設定值不單獨報出來。
- **現況以程式碼為準，原因以註解與設計紀錄為準。** 還沒實裝的功能完全不提；查不到的原因不編，列出來問使用者。
- **機密不外流。** 金鑰、內部位址、個資不進大綱、分鏡、旁白。使用者確認腳本之前，旁白不送到外部的配音服務。
- **一個場景只講一個概念；畫面比旁白先到。**
- **先確認內容，再確認分鏡，最後才花時間渲染。**

`<skill>` 代表本檔所在的資料夾。所有產片動作都透過 `<skill>/scripts/arch-video.mjs`，
不要自己寫 HTML，也不要直接呼叫 hyperframes。

素材可以是一個 repo，也可以是程式碼、skill、技術文件混在一起的一批東西。
設計時主要的對象是 skill、MCP server 與中小型的程式專案；其他類型可以做，先告訴使用者這一點。

**工作資料夾**：大綱、分鏡、預覽都放在這裡。使用者有指定就照指定；沒指定就用主要程式碼所在 repo 的 `docs/video/`，
沒有 repo 就用目前資料夾下的 `video/`。下面用 `<work>` 代表它。
素材跨好幾個 repo，或使用者要求不要動專案時，用目前資料夾下的 `video/<名稱>/`，架構圖也存在那裡。

## 工作流程（依序執行；只在步驟 3 和步驟 8 停下來等使用者）

### 0. 體檢

```bash
node <skill>/scripts/arch-video.mjs doctor
```

- 有「缺」：照它列的方法補。要安裝或下載東西之前，先用一句話告訴使用者要裝什麼，再執行。
  相依套件用 `npm install`（在 `<skill>` 裡執行）。
- 體檢會向配音服務送一句固定的測試文字來確認連線，內容和專案無關。
- 只有「注意」：可以繼續。體檢顯示配音連不上時，成品會是沒有聲音的純字幕版，要在步驟 8 告訴使用者。

### 1. 清點素材、確定範圍

先讀 `<skill>/references/source-rules.md`，步驟 1 到 6 都照它做。

- 列出收到的每一份素材和它的類型（程式碼、隨程式維護的說明、技術文件）。
- 確定這支影片要講的範圍：專案本身，加上使用者點名的額外功能或延伸主題。使用者沒有特別說，就只講專案本身。
- 不讀 `.env`、金鑰檔、憑證。

### 2. 整理與對齊

- 先讀程式碼，再讀技術文件。進入點、設定、核心模組一定要讀到。素材量大就分給子代理讀。
- 讀的時候順手收集原因：常數與設定旁邊的註解、設計紀錄、教訓紀錄、`git log` 的 commit 訊息。
- 把內容整理成 `<work>/brief.md`，格式見 `source-rules.md` 的「內容大綱的格式」：
  - **為什麼需要它**：它解決什麼問題、誰會遇到。開場從這裡寫。
  - **主題與事實**：每一條事實附出處（`路徑:行號`）。
  - **架構拆解**：分區、節點、主要資料流，以及圖外的對象。這時還不畫圖。
  - **決策**：每個關鍵的決定一條，寫明問題、選擇、原因、沒採用的做法、影響、帶得走的做法。影片的主體由這一節組成。
    原因有出處才算數；查不到就標「不明」，不可以編。
  - **排除清單**：未實裝的、只有文件提到的、機密或個資。
  - **不一致**：文件和程式碼對不上的地方，以程式碼為準。
  - **需要確認**：拿不準的事、沒讀到的部分。
- 另外建立 `<work>/.gitignore`，內容是一行 `out/`，產出才不會被 commit。

### 3. 審核點一：內容確認（停下來）

用一則訊息給使用者下面七樣，然後停下來等回覆。訊息是摘要，不重複大綱的出處；附上 `brief.md` 的完整路徑。

1. **它解決什麼問題**：一到兩句。這會是影片的開場。
2. **要講的主題**：每個主題一句話。
3. **架構拆解**：分區、每區的節點、主要資料流。參考了文件的哪些分層或名稱也說明。
   主要資料流的另一端是圖外的對象（外部服務、資料庫）時，問使用者要不要把它畫成節點。
4. **打算講的決定**：每個決定一行，寫出選擇和原因。
   **原因不明的另外列成問句**，請使用者每條回一句話；這是影片內容最重要的來源之一。
5. **排除清單**：哪些內容不會出現在影片裡，以及原因。
6. **不一致**：文件和程式碼哪裡對不上，影片採用哪一邊。
7. **需要確認的事**，以及素材讀了多少。在素材裡發現寫死的金鑰、內部位址或個資時，在這裡告訴使用者類型和位置（不含值），
   並提醒大綱裡有這些位置，要不要進版控由使用者決定。

訊息裡同樣不可以出現機密的值。使用者要求修改就改大綱，再給一次。使用者放行後才往下。
使用者回覆的決定記進 `brief.md` 的「審核點一的決定」，後面的步驟只看大綱。
使用者補上的原因寫進對應的決策，出處標「使用者說明」。

使用者事先說過不要停下來：照預設往下做，原因不明的決定不講原因、它的數值也不單獨講，
並在交付時把那些問句列給使用者。

### 4. 畫架構圖

- 用 **arch-blueprint** skill 依程式碼畫，存到主要 repo 的 `docs/architecture/overview.svg`。
  沒有 repo、素材跨好幾個 repo，或使用者要求不要動專案時，存到 `<work>/overview.svg`。
  - **技術文件裡已經有架構圖也要重畫**，文件的圖只參考分層方式和分區名稱。
  - arch-blueprint 規定「畫之前先給使用者確認拆解」。使用者在審核點一確認過的拆解就是這個確認，
    照它畫，不要再問一次。畫完跑它的檢查腳本。
  - 已經有一張符合目前程式碼的圖就直接用，並在審核點二說明是沿用的。
  - 沒有 arch-blueprint skill：停下來告訴使用者需要安裝它，或由使用者決定做一支不含架構圖的影片。

### 5. 寫腳本

先讀 `<skill>/references/script-rules.md`，照它寫。**只從 `brief.md` 寫**，不回頭從原始素材找新內容；
發現大綱缺東西，先補大綱（附出處）再寫。

- **大綱是素材庫，不是腳本的目錄。** 不要把事實逐條變成場景。照 `script-rules.md` 的「四條主線」挑：
  - 開場從「為什麼需要它」寫。
  - 主體先跟著架構圖走，再以「決定」為單位講：所求、選擇、因為、不然、影響、帶得走的做法。
    每一章挑兩到三個最有收穫的決定講深。每個決定掛在圖上的一個節點或一條連線上。
  - 每個上畫面的數字都要講原因或影響，並換算成一個具體的情況。
  - `file`、`terminal`、`tree` 只用來佐證剛講過的主張，不超過場景總數的三分之一。
  - 旁白講做什麼、為什麼、交給誰；函式名、參數、行號不講，選項與錯誤碼不逐一列舉。
  - 每個場景問一次：拿掉它，觀眾會少理解一塊，或少學到一件事嗎？不會就拿掉。

- **長度沒有預設值，由要講的內容決定。** 骨架的四段都要有，每一段的場景數跟著內容量走，講完就停。
  不為了湊長度或把元件用齊而加場景；小專案每一段都取下限（見 `script-rules.md` 的「取捨的標準」）。
  - 使用者有指定長度就照指定的做。內容放不進去時，在審核點二列出打算省略的主題，由使用者決定。
- 骨架固定是四段，細節見 `script-rules.md` 的「整支影片的骨架」：
  1. **開場從需求出發**：情境 → 痛點 →「如果…呢？」→ 專案登場 → 預告。不要一開始就介紹專案。
     開場的形式跟著痛點選（對話、一次事故、重複的手動步驟、卡住的工具），不要每支都用對話框。
  2. **核心想法**：一兩句主張，加上關鍵數字。
  3. **架構與細節**：架構圖要逐區講解，再跟著資料把每一條主要連線走一遍，然後才補規則與用法。
     使用者點名的額外功能，每一個各自成一章放在這一段的後面。
  4. **完整的結尾**：重點回顧 → 適合與不適合 → 怎麼開始 → 一句帶走的話 → 片尾卡。至少四個場景。
- **表現方式要有變化**：同一種元件不連續超過兩次；三分鐘以上的影片至少用六種元件。
- **用圖形講，不要唸投影片**：數量、時間、進度、狀態、流程用 `layout` 的零件畫出來，而且讓它隨旁白變化。
  純文字的場景不超過四成、不連續超過兩個；每個決定至少有一個用圖形講的場景。
- **畫面比旁白先到**：程式會讓元素在旁白講到它的那個子句之前出現。觸發詞要挑旁白第一次講到那個元素的地方。
- **講到功能或行為的旁白，都要對得到大綱裡的編號。** 對不到的不要寫。串場的句子不用。
- **講到原因的旁白，都要對得到大綱裡一條有出處或有推導的原因。** 不可以為了讓故事完整而補一個原因。
  開場的情境例子可以虛構，但要用「想像一下」這類說法標明，而且痛點要對得上大綱的「為什麼需要它」。
- **排除清單裡的內容完全不提**，包括「未來會支援」這種說法。可以講現在的行為與限制。
- **`file` 場景顯示的是檔案原文。** 可以省略整行、可以從行尾截斷並加上「…」、可以去掉 Markdown 的粗體與反引號記號，
  不可以改寫用字。含有機密的行不要選；非顯示不可時把值換成 `••••`。

### 6. 寫分鏡

照 `<skill>/references/storyboard-format.md` 的格式，寫到 `<work>/storyboard.json`。
範例見 `<skill>/examples/demo/storyboard.json`。

- `map` 場景的 `svg` 路徑相對於分鏡檔，通常是 `../architecture/overview.svg`；架構圖存在 `<work>` 時就是 `overview.svg`。
- 專有名詞列在 `meta.properNouns`；其他英文詞在 `say` 改成中文說法。
- 每一章寫 `short`（四個字以內的中文名稱），左上角才會顯示成一排章節、目前這一章亮起來。
- 寫完後拿大綱的「排除清單」逐項對照旁白和畫面上的文字，確認沒有任何一項混進去。

### 7. 預覽

```bash
node <skill>/scripts/arch-video.mjs build <work>/storyboard.json --stills-only --out <work>/out
```

**預覽不會配音。** `--stills-only` 不連配音服務，時間用字數估算；使用者在審核點二確認腳本之前，
旁白不會送到外部。不要加 `--voice`，也不要在這一步執行沒有 `--stills-only` 的指令。

- 報錯就修分鏡；警告也要全部處理到沒有為止。
  - 「疑似機密或個資」會直接報錯並停止。把那段內容從分鏡拿掉，或把值換成 `••••`，再重跑。
  - **不可以自己把字串加進 `meta.allow`。** 你認為某個被擋下的字串可以公開、而且影片需要它，
    先拿掉它讓預覽跑完，在審核點二提出來；使用者明確同意後才加進去。
- **實際打開 `<work>/out/<name>/stills/sheet.jpg` 看圖**，逐一確認：
  - 文字沒有超出畫面、沒有互相重疊。
  - 每個場景只看畫面就說得出它在講什麼。
  - 強調色只落在那個場景的重點上。
  - 同一種元件沒有連續超過兩次；架構圖拉近時，被講到的節點清楚可讀。
  - 總表看起來不是一整排文字卡片：講數量、過程、狀態的場景有畫成圖形。
- 有問題就改分鏡再跑一次，直到通過。

### 8. 審核點二：分鏡確認（停下來）

用一則訊息給使用者下面五樣，然後停下來等回覆：

1. **故事線**：三到五行。從什麼需求講起、核心想法是什麼、架構怎麼走、講了哪幾個決定、最後讓觀眾帶走什麼。
2. **腳本**：一張表，每個場景一列，欄位是「場景、元件、旁白、根據」。「根據」填大綱的編號。
   唸法和字幕不同的句子要標出來。
3. **預覽總表**：把 `sheet.jpg` 傳給使用者（或給完整路徑），並寫出預估長度。
   長度是用字數估的，實際配音後會有出入。
   預覽圖是每個場景的最後一個畫面；架構圖中途的鏡頭要等渲染後才看得到，這一點要說明。
4. **架構圖**：是新畫的還是沿用的。
5. **不確定的地方**：你做的假設、省略的主題、示意用的終端機輸出、被機密掃描擋下而想請使用者放行的字串、
   體檢顯示配音連不上等限制。
6. **放行後會發生的事**：旁白的文字會送到外部的配音服務合成語音。

使用者要求修改就改分鏡、重跑步驟 7，再給一次。使用者放行後才往下。

使用者說過這一步改由另一個代理或模型審核：把 `references/review-checklist.md` 交給審核者，
照它的發現修到通過，再往下。審核的結論與沒有照改的項目在交付時告訴使用者。
使用者同意放行的字串，這時才加進 `meta.allow`（要和被擋下的內容完全相同）。

### 9. 渲染

```bash
node <skill>/scripts/arch-video.mjs build <work>/storyboard.json --out <work>/out
```

這一步才會配音。結束時它會印出「成品檢查」：長度、有沒有畫面、有沒有聲音。以非零結束就是失敗，照錯誤訊息處理，不要回報成功。

- 實際配音的時間和估算不同，可能出現預覽時沒有的警告（例如元素比旁白晚出現）。調整觸發點後重跑；
  只改觸發點和時間不用再回審核點二，改到旁白或畫面內容才要。
- 配音只成功一部分（例如句數多、服務要求放慢）：指令會停下來、不渲染。過幾分鐘執行同一個指令，
  已經配好的句子會用快取，只補配缺的。
- 「配音服務連不上」的警告不是分鏡的問題，改分鏡消不掉。成品會是純字幕版，在步驟 10 告訴使用者。

### 10. 交付

告訴使用者：

- 影片的完整路徑與長度。
- 還留著的警告。
- **你沒有驗證的事**：你聽不到聲音，所以配音的音質、語調、畫面和語音是否同步，都要請使用者自己聽過。

## 不可以做的事

- 不把影片做成程式碼的逐檔導讀；不為了把事實講完或把元件用齊而加場景。
- 不提還沒實裝或打算做的功能，也不把文件裡的說法當成程式的現況。
- 不編原因。素材裡查不到、使用者也沒說的原因，不可以用聽起來合理的說法補上。
- 不把數字、設定值、流程步驟單獨報出來而不講原因或影響。
- 不把金鑰、密碼、內部位址、人名、電子郵件寫進大綱、分鏡、旁白、架構圖，也不寫進給使用者的訊息。
- 不讀 `.env`、金鑰檔、憑證。
- 不在使用者確認腳本之前執行會配音的指令（沒有 `--stills-only` 的 `build`，或加了 `--voice` 的預覽），也不自己往 `meta.allow` 加東西。
- 不使用 HyperFrames 的 `publish`、`share`、`cloud`：它們會把專案或影片上傳到外部服務。
- 不修改 `<skill>` 裡的程式、場景元件或主題，除非使用者明確要求。
- 不為了通過檢查而刪掉警告對應的內容；分鏡類的警告代表畫面真的有問題，要修的是分鏡。
